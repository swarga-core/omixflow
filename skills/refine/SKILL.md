# OMIXFlow refine

Уточняет постановку задачи в трекере и, при `--multitask`, раскладывает её на части
с картой зависимостей. Не создаёт локальных файлов, не трогает git. Запускается для
любой задачи, в любой момент, многократно.

Пролог и диалог: `${CLAUDE_PLUGIN_ROOT}/protocol/runtime.md`,
`${CLAUDE_PLUGIN_ROOT}/protocol/dialog.md`. Порт: tracker. Мультизадача:
`${CLAUDE_PLUGIN_ROOT}/protocol/multitask.md`. Профили:
`${CLAUDE_PLUGIN_ROOT}/protocol/profiles.md`.

## Активация

- `/omixflow:refine {id}`: уточнение постановки.
- `/omixflow:refine {id} --multitask`: уточнение плюс декомпозиция на части.
- `/omixflow:refine {эпик}`: уточнение эпика плюс его дочерние задачи (раздел «Эпик»).
- `--lead=NAME` (от `develop`): вопросы в точках решения по `protocol/lead.md`;
  состояния задачи ещё нет, номера вопросов ведёт оркестратор.

Адаптер `none` не имеет описания в трекере: refine для него не применим, скил
сообщает об этом и предлагает `develop`, где уточнение делается в task.md.

## Алгоритм

### 1. Задача

`get`, `comments` (если есть), связанные задачи через `search`. Не найдена:
проверить ключ проекта, предложить поиск. `--multitask` при адаптере, который в разделе
«Мультизадача» её не поддерживает: СТОП с объяснением, предложить отдельные задачи
(где адаптер умеет, под общим родителем).

### 2. Контекст (при необходимости)

Если задача техническая и из описания неясно, о чём речь, прочитать ключевые файлы:
публичный API затрагиваемого пакета, README, типы. Цель: понять предметную область,
чтобы задать правильные вопросы. Source Files Map и scope здесь не строятся, это
работа research.

### 3. Анализ

Неясности; пробелы (edge cases, ошибки); неоднозначности; зависимости и блокеры;
критерии приёмки и их конкретность. Если в трекере есть блок мультизадачи, а
`--multitask` не передан, работать с постановкой в целом, блок не трогать.

### 4. Диалог

Вопросов нет: сказать «постановка полная», перейти к записи только если что-то
всё же меняется. Есть: спросить в точке `statement`.

### 5. Уточнённая формулировка

```markdown
## Уточнённая формулировка

{полная, однозначная постановка}

### Критерии приёмки
- {критерий}

### Ограничения
- {что задача не делает}
```

### 6. Запись

Превью целиком, затем подтверждение в точке `tracker.describe`: Записать (Recommended) /
Поправить / Пропустить. `update_description` адаптера: исходное описание сохраняется, секция
добавляется или заменяется, если уже была. Дисциплина записи: прочитать перед
записью, менять только свою секцию, перечитать после. Адаптер отклонил запись, потому
что задача уже в работе и постановкой владеет её сессия (трекер с `artifacts`): сказать
об этом и предложить передать уточнение сессии задачи.

### 7. Итог

```
Задача {id} уточнена. Вопросов: {N}. Трекер обновлён: да/нет.
Начать: /omixflow:develop {id}
```

## Эпик

Задача — эпик (родитель дочерних задач, раздел «Эпики» адаптера): шаги 1–6 уточняют
эпик в целом (цель, границы, критерии готовности), затем дочерние задачи:

1. Уже созданные дочерние задачи по разделу «Эпики» адаптера: показать, не дублировать.
2. Состав в точке `decomposition`: по каждой новой дочерней задаче название, тип
   и короткая постановка с критериями приёмки. Каждая — самостоятельная задача
   пайплайна; зависимость между ними пишется в постановку, связь (`link`) по слову
   разработчика. Разработчик может завести только часть: остальные пункты остаются
   в уточнённой формулировке эпика списком `### Ещё не заведены`, по нему эпик не
   закроют раньше времени.
3. Превью списка, затем подтверждение в точке `tracker.describe`: Записать (Recommended) /
   Поправить / Пропустить. Создание — `create` адаптера с родителем-эпиком. Текст
   дочерней задачи: строка происхождения («часть эпика {id}») и секция
   `## Уточнённая формулировка` с критериями приёмки — постановка уточнена в диалоге
   эпика, Start не предложит refine повторно. Заведённые пункты убрать из
   `### Ещё не заведены` эпика (`update_description`). Трекер с возможностью `batch`
   (`PORT.md`, «Пакетная запись»): дочерние задачи, связи между ними по слову разработчика
   и правка постановки эпика — одной пакетной записью, связи ссылаются на новые задачи
   по их временным именам; без возможности — по одной записи.
4. Итог: id созданных задач и запуск каждой: `/omixflow:develop {id}`.

`--multitask` для эпика не применяется: части мультизадачи живут в одной задаче,
дочерние задачи эпика — отдельными задачами трекера.

## Режим `--multitask`

Дополняет шаги 3–6. Вопросы пунктов 0–2 задаются в точке `decomposition`.

0. **Профиль.** Один раз: `full` (Recommended) / `research` (исследование без
   изменения кода, части параллельно) / другой из `profiles.md`.
1. **Декомпозиция.** Обсудить с разработчиком части: slug (kebab-case, уникален,
   после старта не меняется), title, краткая постановка каждой части. Каждая часть
   это самостоятельный квант: проходит пайплайн выбранного профиля, своя ветка
   и worktree только при `part_isolation: worktree`. В мутирующем профиле часть,
   требующая изменений в двух репозиториях, разбивается; в немутирующем часть читает
   ровно один репозиторий.
1a. **Репозиторий части** (немутирующий профиль): по каждой части спросить репозиторий
   из `workspace.repos` (`resolve.py repo --list`) или домашний (`—`).
2. **Карта зависимостей, обязательна и явная.** По каждой части спросить, от каких
   частей она зависит; ответ «ни от чего» тоже ответ и пишется как «—». Пустых ячеек
   не бывает. Помочь разработчику: части, которые меняют один и тот же контракт или
   читают результат друг друга, зависимы.
3. **Валидация.** Сохранить текущее описание во временный файл в scratchpad и:
   ```bash
   repos=$(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.py" repo --list)
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/multitask.py" seed --from {desc.md} \
     --parts "{slug} — {title}" ... --depends "{deps}" ... \
     --profile {profile} [--repo "{repo|—}" ...] --repos "$repos" > {desc.new.md}
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/multitask.py" validate --from {desc.new.md} --repos "$repos"
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/multitask.py" waves --from {desc.new.md}
   ```
   Показать волны разработчику: это ответ на вопрос, что можно делать параллельно.
   Цикл или неизвестная зависимость: вернуться к п. 2; неизвестный репозиторий:
   к п. 1a.
4. **Запись.** Превью блока и волн, затем подтверждение в точке `tracker.describe`.
   `update_description`
   всем текстом из `desc.new.md`; блок оказывается в хвосте описания. Если адаптер
   поддерживает `tag`, добавить тег `multitask` (отказ не критичен).
5. **Повторный refine мультизадачи.** Блок уже есть: не сидить заново. Изменения
   состава частей: новые части — `multitask.py add-part --part "{slug} — {title}" --depends
   "{deps|—}" [--repo …]` (статус `pending`, ответ про зависимости обязателен, как в п. 2),
   лишние — `multitask.py set … status=skipped`; статусы существующих не трогать; показать дельту
   и записать с подтверждением в точке `tracker.describe`. Если мультизадача стартована,
   напомнить, что
   постановки частей после старта правятся в `multitask.md`, и предложить
   синхронизировать его.

Части не становятся задачами трекера; борд статусов создаёт refine со всеми
`pending`, дальше им управляет пайплайн.

## Повторный запуск

Секция уже есть: показать её и спросить в точке `resume`: Оставить (Recommended) /
Доработать.

## Правила

- Никаких локальных файлов и веток.
- Исходное описание не удаляется.
- Запись только с подтверждением и полным превью.
- Многократность: каждый запуск может дополнить формулировку.
- Карта зависимостей без явного ответа по каждой части не записывается.
