# OMIXFlow create

Создаёт задачу в трекере из черновика. Анализирует идею, исследует код, выявляет
edge cases и затронутые системы, обсуждает с разработчиком, формирует выверенную
постановку. **Локальных артефактов, веток и `.tasks/{id}/` не создаёт.**

Пролог, адаптеры, диалог: `${CLAUDE_PLUGIN_ROOT}/protocol/runtime.md`,
`${CLAUDE_PLUGIN_ROOT}/protocol/dialog.md`. Порт: tracker (возможность `create`
обязательна; без неё скил сообщает, что адаптер задачи создавать не умеет).

## Активация

- `/omixflow:create "{черновик}"` из свободного описания.
- `/omixflow:create --from {local-id}` из файла локального трекера
  (`tracker.dir`, адаптер `local`): черновик читается из файла, после создания
  в файл записывается `external: {id}` и статус `done`.
- `/omixflow:create` без аргумента: спросить описание.

## Алгоритм

### 1. Черновик

Получить текст. Определить тип (баг, фича, рефакторинг, документация, долг),
ключевые слова, достаточность. Если невозможно понять даже область, задать
уточняющие вопросы до исследования.

### 2. Исследование

Спавн `researcher` (`resolve.py agent researcher`) по шаблону runtime.md
с `TASK_DRAFT` (текст черновика), `OUTPUT: inline`, `ADAPTERS.lang`. Запрос:
затронутые пакеты и файлы, текущее поведение, существующие паттерны, зависимости
и side effects, ограничения архитектуры. Формат ответа: Source Files Map, Findings,
потенциальные проблемы. Оркестратор код не исследует сам.

### 3. Анализ и вопросы

Из черновика и исследования: edge cases; затронутые системы, о которых
разработчик мог не подумать; конфликты с паттернами; варианты подхода; пробелы.

### 4. Диалог

Перечислимое через AskUserQuestion (до четырёх за вызов, рекомендуемый первым),
остальное текстом. Если вопросов нет, сказать об этом и перейти к постановке.

### 5. Постановка

```markdown
## Описание
{чёткое описание проблемы или фичи}

## Контекст
{как работает сейчас, что затронуто, почему нужно менять}

## Требования
- {требование}

## Критерии приёмки
- {критерий}

## Ограничения
- {что не входит в scope}

## Затронутые компоненты
- {пакеты, модули, файлы}
```

Если задача по сути мультизадача (несколько независимых частей), сказать об этом
и предложить после создания запустить `/omixflow:refine {id} --multitask`.
Блок частей на этапе create не пишется.

### 6. Метаданные

Summary до восьмидесяти символов. Поля из `tracker.create_defaults`; enum-поля,
которые адаптер умеет читать (`get schema`), уточнять через AskUserQuestion только
когда тип задачи неочевиден. Обязательные поля и запреты для типов описывает адаптер
и его проектное расширение, не скил.

### 7. Подтверждение и создание

Гибрид: полное превью текстом (summary, поля, постановка целиком), затем
AskUserQuestion: Создать (Recommended) / Поправить / Отменить. При подтверждении
`create` адаптера; при `--from` затем `update` локального файла: `external`,
`status: done`, запись в журнал.

### 8. Итог

```
Задача создана: {id}
{url, если адаптер даёт}
Уточнить: /omixflow:refine {id}
Начать: /omixflow:develop {id}
```

## Правила

- Никаких локальных файлов, кроме обновления файла локального трекера при `--from`.
- Исследование только через агента.
- Создание только с подтверждением и полным превью.
- Не додумывать за разработчика: неочевидное превращается в вопрос.
- Постановка обязана быть существенно полнее черновика; в этом смысл скила.
