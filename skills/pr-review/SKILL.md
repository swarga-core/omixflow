# OMIXFlow pr-review

Качественное ревью чужого PR или локальной ветки: чтение кода и тестов, проверка
соответствия архитектуре проекта, сверка с project specs затронутых слайсов,
диалог по findings с ревьюером-человеком, публикация структурного ревью.

Пролог: `${CLAUDE_PLUGIN_ROOT}/protocol/runtime.md`. Диалог:
`${CLAUDE_PLUGIN_ROOT}/protocol/dialog.md`. Worktree и ловушки:
`${CLAUDE_PLUGIN_ROOT}/protocol/worktree.md`. Порты: forge (для PR нужны
`pr_get`, `pr_files`, `pr_reviews`, `pr_threads`, `review_publish`, `reply`,
`permalink`), lang, workspace, tracker (опционально, для комментария по ветке).

Скрипт форджа: `PR=$(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.py"
adapter-script forge pr)`. Все обращения к хостингу идут через него; команды
адаптера скил не знает.

## Активация

- `/omixflow:pr-review {number|url}`: ревью PR; при наличии моего опубликованного
  ревью автоматически режим re-review.
- `/omixflow:pr-review {pr} --fresh`: полное ревью с нуля, игнорируя историю.
- `/omixflow:pr-review --branch {name} [--base {base}]`: ревью локальной ветки без
  публикации; результат в `.review/{name}/review.md`, по желанию комментарием
  в трекер.

## Принципы

1. **Артикулировать проблемы, не предписывать решения.** Реализацию выбирает автор.
2. **Формат пункта:** цитата кода, пронумерованные аспекты «что не так», возможные
   направления без инструкций.
3. **Группировка по типу замечания**, не по файлам: видны системные паттерны.
4. **REQUEST_CHANGES при пунктах в группах A или G.** Иначе COMMENT. APPROVE
   в fresh-режиме скил не публикует; в re-review APPROVE легален (R6.5).
5. **Подпись `— {имя из current_user}`** в теле ревью, без упоминания ИИ.
   В ответах внутри тредов подписи нет.
6. **`.review/` под gitignore**, артефакты не коммитятся.
7. **Файлы PR не редактируются, даже временно.** Никаких probe-правок и probe-тестов
   в worktree ревью: гипотезы проверяются чтением кода и запуском существующих
   гейтов и тестов. Worktree PR это чужая ветка, правка там читается как
   вмешательство в предмет ревью.
8. **Re-review бережёт контекст обсуждения:** ответы только в свои треды, чужие
   по явной просьбе, resolve тредов оставляем автору, research только по дельте.

## Артефакты

```
.review/
├── _repo-context.md          репо-уровневый контекст, общий для всех PR этого репо
└── {name}/                   имя из ветки (task/AL-881 → AL-881)
    ├── review.md             черновик дискуссии: группы, статусы пунктов
    ├── pr-body.md            тело ревью текущего раунда
    ├── pr-comments.md        inline-комментарии текущего раунда
    ├── payload.json          собранный payload (скрипт адаптера)
    ├── arch-snapshot.md      PR-специфичные архитектурные выводы и снапшот спек; живёт между раундами
    ├── history.md            re-review: инвентарь моих тредов
    ├── replies.md / .json    re-review: ответы в треды
    └── archive/round-{n}/    артефакты прошлых раундов
```

`_repo-context.md` про проект; `arch-snapshot.md` про PR. Имена внутри `{name}/`
короткие, без префикса.

## Алгоритм: fresh review

### 1. Discovery

```bash
$PR view {pr}          # owner, repo, number, title, head_ref, head_sha, base_ref, author, body
$PR files {pr} --names
git log --oneline {base_ref}..{head_sha}
```

Сохранить `OWNER`, `REPO`, `PR_NUMBER`, `HEAD_SHA`, `BASE_REF`, `NAME`.
Создать `.review/{NAME}/`, добавить `.review/` в `.gitignore`, если ещё нет.

**Re-review detect** (без `--fresh`): `$PR reviews-mine {pr}` даёт `rounds`
и `previous_sha`, считая только настоящие ревью (с вердиктом или непустым телом:
хостинг пишет каждый ответ в тред отдельной пустой записью, они не раунды).
`rounds == 0` → fresh. Иначе `ROUND = rounds + 1`; `previous_sha == HEAD_SHA` →
выйти: «PR не изменился с {sha}; полное переревью: `--fresh`». Иначе → раздел
«Re-review».

**Working tree alignment** (критично: без этого агенты читают не тот код):
`git rev-parse HEAD == HEAD_SHA` → `aligned`. Иначе AskUserQuestion:

1. **Worktree** (Recommended): `git worktree add .claude/worktrees/pr-{n} {HEAD_SHA}`,
   `EnterWorktree({path})`, затем **setup по адаптеру workspace** (инициализация
   submodule'ов, установка зависимостей): без этого гейты падают на неразрешённых
   пакетах и это выглядит как дефект PR. Артефакты `.review/` в изолированной
   сессии держать внутри worktree и копировать обратно простым `cp`.
2. **Checkout** ветки PR в текущем дереве: только при чистом `git status`.
3. **git show fallback**: агентам явная инструкция читать файлы PR через
   `git show {HEAD_SHA}:{path}`; только для маленьких PR.

`WORKING_TREE_MODE` ∈ aligned | worktree | checkout | git_show.

### 1.5. Context bootstrap

Если `.review/_repo-context.md` есть, прочитать и пропустить. Иначе собрать
briefing до двухсот строк. Короткий путь: если корневой CLAUDE.md проекта
полноценный, `_repo-context.md` это тонкая обёртка (не больше сорока строк):
«первоисточник: прочти CLAUDE.md целиком» плюс то, чего там нет: оглавление
`docs/`, submodule-специфика из адаптера workspace, ссылки на глубокие доки
затронутых пакетов. Дублировать CLAUDE.md запрещено. Полный путь при скудном
CLAUDE.md: тип репо (по адаптеру workspace: submodule'ы, монорепо), пакеты и граф,
архитектура слоёв, конвенции ревью (из адаптера lang: подавления, тесты),
ключевые ссылки, gotchas. Файл переиспользуется между PR этого репо; при
структурных изменениях удалить вручную.

### 2. Research

Параллельно два Explore-агента (субагенты не получают CLAUDE.md проекта, промпт
обязан перечислить источники):

- **Архитектура**: прочитать `_repo-context.md`, CLAUDE.md, адаптеры lang,
  документацию затронутых пакетов, публичные поверхности; вернуть ключевые API
  с цитатами, конвенции, идиомы и **точки конфликта с этим PR**.
- **Diff**: прочитать `_repo-context.md`, затем каждый файл из списка diff'а;
  по каждому: что меняется, в какой слой попадает, как вписывается в архитектуру;
  особое внимание новым use case, портам и адаптерам проекта, диалогам, тестам,
  публичным экспортам. Вернуть по группам файлов.

При `WORKING_TREE_MODE != aligned` промпт содержит правило чтения (абсолютные
пути worktree или `git show`). После агентов лично подтвердить ключевые находки
чтением. Сохранить `arch-snapshot.md`: цитаты API, границы слайсов, состояние
project specs (путь и короткий хеш), HEAD_SHA.

### 3. Spec drift

По SDD-конвенции проекта (CLAUDE.md, документация) найти project specs
затронутых слайсов; проверить, обновлены ли они в diff'е; сравнить spec с кодом:
новые типы и use case без описания, решения, противоречащие коду без пометки
superseded, нетривиальные архитектурные решения без decision. Спека проектного
слоя нужна так же, как спека библиотечного: её отсутствие это G-пункт, а не
исключение. Артефакты пайплайна автора (`.tasks/`) не требуются и не проверяются.

### 4. Compile findings

| Группа | Содержание |
|---|---|
| A. Критические баги и блокеры | реальные баги, гонки, хардкод боевых значений, обход слоёв и фасадов проекта, отсутствующие ключи локализации на основной локали |
| B. Архитектурные расхождения | нарушения слоистости, неиспользование общих пакетов проекта, неполные публичные экспорты, несогласованность типизированных ошибок |
| C. Незаконченное | заглушки в продакшен-коде, hardcode вместо параметризации, задел «на потом» |
| D. Качество кода | дублирование, мёртвый код, устаревшие паттерны, хрупкие хаки, неудобные приведения типов |
| E. Тесты | дублирование, утечка состояния между файлами, долгие ожидания, отсутствие негативных кейсов, подавления из адаптера lang |
| F. Workspace | только при `workspace.submodules`: указатель submodule обновлён и опубликован в origin его репозитория, соблюдены read-only правила |
| G. Spec drift | project specs затронутых слайсов не обновлены (шаг 3) |

Каждая находка: **где** (файл:строка, permalink с pinned HEAD_SHA через
`$PR permalink`), **что не так** (3–5 аспектов), **возможные направления** (2–4,
без инструкций).

### 5. Черновик

`review.md`: цель, формат пункта, карта групп, развёрнутые пункты A, однострочники
остальных групп в `## Pending`. Статусы: Included / Note (deferred) / Excluded /
Pending review.

### 6. Диалог

Сводка PR текстом (что сделано, оценка, карта групп с числами). Затем группа A
в расширенном формате, решения через AskUserQuestion по одному вопросу на пункт,
до четырёх за вызов: Включить (Recommended) / Note (deferred) / Исключить;
переформулировка через Other → текст. Дальше B, C, D, E, F (если применимо), G.
Текстовый override «включаем всю группу» допустим. Не предлагать автору
конкретные решения. Итог: счётчики по группам.

### 7. Build

**`pr-body.md`**: заголовок «Code Review — {NAME}: {title}»; что в PR; общая
оценка; карта замечаний (таблица группа / количество / примеры); Notes (deferred);
cross-cutting замечания с permalinks; секция G целиком (спеки не в diff'е, inline
невозможен); что дальше; подпись.

**`pr-comments.md`**: блок на комментарий, внешний фенс **четыре бэктика**,
чтобы тело могло содержать вложенные тройные:

```markdown
### {ID} — `{path}`, line {N}          (или lines {A}-{B})

````
**{ID}. {Заголовок}**

{проблема, аспекты, направления; вложенные ```код``` допустимы}
````
```

Multi-file: одна проблема в двух файлах → один inline плюс permalink; паттерн
в N местах → inline на эталонном плюс список; дубликат значения → два inline
со ссылками друг на друга; cross-cutting и G → в теле.

```bash
$PR build-payload --dir .review/{NAME} --sha {HEAD_SHA} --event {REQUEST_CHANGES|COMMENT}
```

### 8. Validate

```bash
$PR validate --dir .review/{NAME} {pr}
```

Строка вне diff hunks не принимается хостингом. Для каждой проблемы: перенести
пункт в тело как cross-cutting с permalink или сдвинуть на ближайшую валидную
строку, если смысл сохраняется; убрать блок из `pr-comments.md`; пересобрать
payload; повторить валидацию.

### 9. Submit

Гибрид: сводка (event, число inline, cross-cutting секции, счётчики), затем
AskUserQuestion: Отправить (Recommended) / Поправить / Отменить.

```bash
$PR submit --dir .review/{NAME} {pr}
```

Ошибка валидации строк на стороне хостинга → шаг 8; ошибка авторизации →
проверить CLI по адаптеру. При rebase PR (новый HEAD_SHA) пересобрать payload
и permalinks.

### 10. Итог

URL ревью, event, число inline и cross-cutting, артефакты в `.review/`.

## Режим `--branch`

Без форджа. `HEAD_SHA` = HEAD ветки, `BASE_REF` = `--base` или base из
`resolve.py base`, diff `{base}...{branch}`. Шаги 1.5–6 те же (permalinks
заменяются на `path:line`), затем итоговый `review.md` с Included-пунктами
в формате тела ревью. Публикации нет; по желанию разработчика комментарий
в трекер через `comment` (гибрид с превью). Полезно для ревью своей ветки перед
PR и для веток без хостинга.

## Re-review

Отдельный поток вместо шагов 2–10.

### R0. Архив

`review.md`, `pr-body.md`, `pr-comments.md`, `payload.json`, `history.md`,
`replies.*` → `archive/round-{ROUND-1}/`. `arch-snapshot.md` остаётся.

### R1. Инвентарь тредов

`$PR threads {pr} --mine` → `history.md`: по каждому моему треду id, id последнего
комментария (для ответа), resolved, outdated, путь и строка, первые двести
символов, `Action: Pending check`. Resolved сразу `Skip`. Чужие треды отдельным
списком со `Skip` по умолчанию. Секция `## Spec updates since previous review`
заполняется в R3.

### R2. Delta research

Убедиться, что оба SHA доступны: `git fetch` head PR и `previous_sha`; если
`previous_sha` осиротел после force-push → **full-diff fallback** (`BASE_REF..HEAD_SHA`)
с пометкой в history.md; контекстные файлы всё равно переиспользуются.
Working tree alignment как в шаге 1 (worktree + setup). Один Explore только
по дельте `previous_sha..HEAD_SHA` с `_repo-context.md`, `arch-snapshot.md`
и `history.md` во входе: что изменилось, какие мои замечания это адресует
(id треда), какие новые проблемы. Архитектурный re-research не нужен.

### R3. Spec drift по дельте

Спеки, изменённые после `previous_sha`, в `history.md`; затронутые слайсы
с изменёнными контрактами без обновления спек → новый G-пункт.

### R4. Compile

`review.md` с двумя секциями: `## Thread replies (reconciliation)` (по треду:
состояние, предлагаемый ответ, статус) и `## New findings (delta)` (группы A–G
только по дельте).

### R6. Диалог в два прохода

**Проход 1, треды.** Матрица: resolved → Skip; unresolved, outdated, проблема
ушла → «verified» без resolve; unresolved, проблема актуальна → ответ с
уточнением; автор задал вопрос → ответ; неясно → углубиться. Гибрид: состояние
и текст ответа текстом, решение через AskUserQuestion до четырёх тредов за вызов.
Чужие треды только по явной просьбе.

**Проход 2, новые находки:** как шаг 6.

### R6.5. Event

Только если есть хотя бы один Included new finding:

| Условие | Event |
|---|---|
| все мои прошлые A/G закрыты и в дельте нет нового A/G | APPROVE |
| остались или появились minor | COMMENT |
| старые A/G не закрыты или новое A/G | REQUEST_CHANGES |

Без new findings батч не собирается, публикуются только ответы. **Особый случай:
автор закрыл все мои треды, дельта чистая, findings нет** → это тоже раунд:
APPROVE с коротким телом-верификацией («проверил дельту {sha}..{sha}, замечания
закрыты»), без inline и без ответов в треды.

### R7. Payloads

`replies.md` и `replies.json` (`[{"in_reply_to": {comment_id}, "body": "..."}]`,
без подписи); батч `pr-body.md` + `pr-comments.md` + payload как в шаге 7, только
из новых findings, заголовок с `(round {ROUND})`, раздел «Что изменилось с прошлого
ревью» вместо «Что в PR», раздел «Reconciliation» только если есть и ответы,
и новые находки.

### R8. Validate

Только `payload.json`; ответы привязаны к id комментариев и не валидируются.

### R9. Submit, строго последовательно

```bash
$PR reply {pr} --file .review/{NAME}/replies.json   # по одному, стоп на первой ошибке
$PR submit --dir .review/{NAME} {pr}                # если есть батч
```

Ответы нельзя класть в батч ревью: хостинг не принимает `in_reply_to` там.
При частичном сбое ответов: не повторять автоматически, сначала проверить через
`$PR threads`, не опубликован ли ответ, затем продолжить с упавшего. При ошибке
остановиться, не откатывать, сообщить, что опубликовано.

### R10. Итог

Ответов опубликовано, новых inline и тело, тредов пропущено, event или «только
ответы», номер раунда, артефакты.

## Анти-паттерны

- Один большой обзорный комментарий вместо ревью с inline: теряется привязка.
- Inline без permalink при ссылке на другой файл.
- APPROVE сразу после fresh-ревью с критическими находками.
- Предложение реализации вместо направлений.
- Payload без черновика дискуссии: пропадает структура для повторных раундов.
- Коммит `.review/`.
- SHA из HEAD на момент чтения, а не на момент сборки payload.
- Правка файлов PR ради проверки гипотезы.
- Запуск агентов на файлах PR при неверном working tree: агент выдумает содержимое.
- Стек PR (base одного = head другого): ревью раздельные, пункты не дублировать.
- Re-review: смешивать ответы и новые inline в одном батче; ответы в чужие треды
  без просьбы; resolve тредов; полный архитектурный Explore; research всего diff'а
  от base при доступной дельте; подпись в ответах; параллельные ответы;
  авто-переход в `--fresh`.
