# Тиры задач: S, M, L

Тир оценивается в начале `develop` по постановке, фиксируется в `state.yaml`
и `task.md`, подтверждается после Refine. Масштабируется содержимое фаз, инварианты
из `phases.md` действуют во всех тирах.

## Критерии

| Тир | Критерии (достаточно большинства) | Отличия потока |
|---|---|---|
| S | точечная правка или баг; не больше `tiers.s_max_files` нетестовых файлов; один пакет или модуль; контракты не меняются; design questions отсутствуют или закрываются одним вопросом на Refine | Research, Spec, Plan инлайн оркестратором в один объединённый spec.md с секциями Research, Scenarios, Steps; Implement через coder на облегчённой модели; Review один проход |
| M | фича или изменение API в одном-двух пакетах; контракты меняются; примерно от 4 до `tiers.m_max_files` нетестовых файлов | architect один вызов в режиме spec+plan и один общий review на оба артефакта |
| L | несколько пакетов, архитектурное изменение, больше `tiers.m_max_files` нетестовых файлов или высокая неопределённость | полный поток без сокращений; researcher на сильной модели |

Пороги считают нетестовые файлы (тесты идут парой к коду и в счёт не входят) — и на
триаже, и по плану («Порог файлов после плана»).

Правила:

- Сомнение между тирами разрешается в пользу большего.
- Тир повышается, если Research вскрыл больший масштаб; понижать нельзя. Поток
  продолжается по новому тиру с текущей фазы. Не выше потолка `tiers.max`; форсированный
  тир не повышается молча — точка `scope-change`.
- Флаг `--tier=S|M|L` форсирует тир и записывается как `forced`. Автоповышение для
  форсированного тира не применяется молча: показать, что вскрылось, и спросить
  в точке `scope-change` (`dialog.md`).
- **Тир из постановки или брифа.** Тир, явно названный в постановке задачи (описание,
  поле трекера, план вехи) или в `brief` лида (поле `tier`), приравнивается к `--tier`:
  develop передаёт в start `--tier={tier} --forced --tier-source={флаг|постановка|бриф}`,
  start пишет в log.md «тир S — постановка» / «— бриф лида». Триаж выше — вопрос в точке
  `scope-change`, не молчаливое повышение и не молчаливое сохранение (G-22, T-4).
- **Потолок тира проекта** — `tiers.max` (по умолчанию `L`). Триаж, давший тир выше
  потолка, ставит потолок: в log.md «тир {триаж} → {max} по tiers.max»; то же у части
  мультизадачи и у умолчания M standalone-запуска. `--tier` выше потолка — отказ
  (`state.py` отклоняет `init --tier` и `set tier=` выше `tiers.max`); тир из постановки
  выше потолка — вопрос `scope-change`: потолок проекта против постановки. `doctor`
  показывает потолок.
- Профиль с `triage: false` (`profiles.md`) не триажится: тир не оценивается, флаг
  `--tier` с ним ошибка, в `state.yaml` хранится `tier: null`. Researcher всегда
  спавнится агентом на `models.strong` и всегда пишет `research.md`; инлайн-ресёрч S
  не применяется.
- Мультизадача сама тиру не подлежит; в профилях с триажем каждая часть триажится
  отдельно при своём Start, с тем же потолком.
- Standalone-запуск фазового скила без триажа работает как M (не выше потолка).

## Порог файлов после плана

Когда план готов (plan.md; в S — `## Steps` spec.md), оркестратор считает его файлы —
до ревью (план, который будет резаться, не ревьюится целиком) и после фиксов:

```bash
python3 {корень плагина}/scripts/plan.py files --task TASK_DIR
```

Уникальные пути строк файлов плана (`CREATE`/`MODIFY`/`DELETE` в любой из форм
architect'а, несколько путей в строке — все), тестовые отдельно (`tests.files` всех
адаптеров lang и их проектных расширений; без шаблонов скрипт говорит «тесты не
отличены» и считает все), порог тира из `tiers.s_max_files` / `tiers.m_max_files`; у L
порога файлов нет, но у всех тиров порог шагов — восемь (`skills/plan`, «Калибровка»).
Код 1 — нетестовых файлов или шагов больше порога; код 2 — план не прочитан или в нём не
распознано ни одной строки файлов (это не «ноль файлов», а форма, которую скрипт не
знает: поправить план или скрипт).

Код 1 — точка `scope-change` с вариантами, в этом порядке:

- **а) срез** (рекомендуется): architect в `MODE: fix` режет вертикально — оставляет
  сценарии, которые вместе со своими слоями укладываются в порог, остальные сценарии и
  их контракты переносит в Out of Scope spec.md и убирает их шаги из plan.md (срез по
  `Covers`, не префикс шагов: порядок шагов — по слоям, и первые шаги не дают ни одного
  сценария целиком). Срез проходит ревью как новый объём (`review-cycle.md`, «Счётчик —
  на объём»). Остаток — задачи-продолжения: трекер с возможностью `create` — создать со
  ссылкой на эту задачу и на перенесённые сценарии, подтверждение в точке `tracker.describe`;
  без `create` — текст разработчику; под лидом — `question` лиду (план вехи или новая
  часть); у части мультизадачи — новая часть через точку `decomposition`;
- **б) тир выше**, если он ниже потолка и не форсирован (форсированный — тот же вопрос,
  но с ответом разработчика или лида);
- **в) продолжить как есть** — решение разработчика (под лидом — эскалация `E-{n}`),
  строкой в log.md, без прецедента: исключение из порога не правило (`lead.md`,
  «Прецедент»); кто бы ни писал его в журнал лида — лид или сама сессия (ответ в окне,
  таймаут, `direct`), — запись идёт с `lead.py decide … --exception`. В SwAIS одно такое
  правило держало планы в M через шесть `scope-change`.

Молчаливого «остаётся M» нет: в SwAIS планы тира M трогали 20–53 нетестовых файла при
пороге 15 (T-1, T-6, T-7, T-11), поток этого не замечал, и стоимость задачи росла вместе с
контекстом каждого агента.

## Модели агентов по тиру

Значение из фронтматтера агента используется, когда ячейка пустая. Оркестратор
передаёт параметр `model` при спавне.

| Агент | S | M | L |
|---|---|---|---|
| researcher | не спавнится | | сильная |
| architect | не спавнится | | |
| coder | облегчённая | | |
| tester | | | |
| reviewer | | | |

При `triage: false` researcher всегда на сильной модели, строка тиров к нему
не применяется.

Имена моделей задаются в конфиге (`models.strong`, `models.light`), чтобы плагин
не устаревал вместе с линейкой моделей. Оркестратор в субагенты не делегирует
собственную модель.

## Смена агента по ходу задачи

Continuation-агент с очень большим контекстом стопорится на длинных командах и дорожает
с каждым сообщением. Оркестратор заводит нового агента той же роли, когда сработал любой
из порогов:

- объём контекста агента больше `limits.agent_rotation_context`;
- coder сделал `limits.agent_rotation_steps` шагов плана.

Порог проверяется перед каждым новым заданием живому агенту: шаг, пакет фиксов,
повторное ревью, переход Spec → Plan, синхронизация. Правило одно для всех продолжаемых
агентов: coder, architect, reviewer и tester, когда ему возвращают задание; ревью кода
к тому же всегда начинает свежий reviewer (`review-cycle.md`, шаг 4). Одного счётчика
шагов мало: планы тира L — 6–9 шагов, а coder набирал 340–500k за один-два тяжёлых шага.

Порог — проверка между заданиями, не потолок: одно задание может поднять контекст агента
выше порога. В T-5 coder-T-5-2 закончил шаг 3 на 237k, а шаг 4 (около 1000 строк,
110 тестов) — на 439k. Прогноз «контекст + рост прошлого задания» по транскриптам прогонов
не годится. Шаг 4 был вторым заданием coder-T-5-2, и поймал бы его только прогноз по первому
заданию; но первое задание агента — знакомство с задачей (170–300k), и такой прогноз
сменял бы агента после первого задания чаще, чем оставлял. Прогноз по повторным заданиям
шаг T-5 не ловит. Перескок одного задания допустим: по прогонам обычно до 440k, наибольший —
491k. Оркестратор по плану агентов не сменяет.

Объём контекста даёт `python3 {корень плагина}/scripts/agent_ctx.py {имя агента}`
по транскрипту агента: уведомление о конце хода именованного агента (режим команд агентов)
usage не несёт, и в MEW-2 проверка молча не состоялась — coder дошёл до 718k при пороге
350k. Скрипт печатает `context`; `context: null` (код 3) с причиной — объём берётся из
уведомления о завершении, если в нём есть usage, иначе в log.md один раз на агента пишется
«контекст {имя} неизвестен: {причина}»: coder сменяется только по шагам, у остальных ролей
смены по объёму нет, пока скрипт не даст объём (проверка — перед каждым заданием).

Новый агент получает имя с суффиксом (`coder-{id}-2`, `reviewer-{id}-code-2`), спавн по
шаблону `runtime.md` и параметр `PREVIOUS_REPORTS`: пути к отчётам предшественника
(`reports/`, `review/`) и log.md. Сделанное он узнаёт из них и из дерева, а не из
пересказа в промпте. Смена: `state.py set TASK_DIR agents.{ключ}={имя}` (ключ роли,
ревьюер кода — `reviewer_code`), строка в log.md
«ротация {role}: {старое имя} → {новое}, контекст {N}k | шагов {M}».
