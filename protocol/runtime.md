# Рантайм скила

Как любой скил OMIXFlow начинает работу, где берёт конфиг, адаптеры и состояние,
как спавнит агентов. Скилы ссылаются сюда и не пересказывают.

## Чтение протокола

Скил в прологе называет, что читать **сначала** — секции протокола по именам — и что
читать **по условию**: «{условие} → {файл} «Секция»». Файл целиком читается только там,
где скил так говорит: короткие `dialog.md` и `phases.md`; `multitask.md` по условию;
`lead.md` читает целиком только скил лида, сессии задач — секции, названные в п. 7 пролога.
Секцию печатает одна команда с литеральными путями (названия в «…», кавычки shell не нужны):

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.py" section runtime.md «Отчёт агента» «Гейты»
```

Секция — заголовок `##` или `###` либо ярлык абзаца `**…**`; заголовок внутри блока кода
(шаблон) границей не считается, `###` входят в свою `##`. Read с offset и limit тоже
проходит в изолированной сессии (по транскриптам — 255 чтений файлов плагина без отказов),
но границы секции он не знает. Остальной протокол не читается впрок: в прогонах 0.5–0.7
сессия читала 12–20 файлов плагина (110–175k символов) до первого действия, и эти 65–80k
токенов сидели в каждом из 250–330 запросов — пятая часть стоимости оркестратора (замер
`cost.py`). Правило, нужное по ходу фазы, скил называет на месте с файлом и секцией.
Перечитывание после сжатия контекста — «Пролог скила», п. 8.

## Пролог скила

1. **Корень плагина**: `${CLAUDE_PLUGIN_ROOT}`. Все скрипты и протокол адресуются
   от него: `"${CLAUDE_PLUGIN_ROOT}/scripts/state.py"`, `"${CLAUDE_PLUGIN_ROOT}/protocol/…"`.
   Переменная пуста (плагин подключён каталогом скилов, например симлинком
   `~/.claude/skills/omixflow`): корень это каталог на два уровня выше `SKILL.md`
   загруженного скила. В командах корень подставляется буквально, абсолютным путём:
   изолированная worktree-сессия отклоняет команды с переменными shell
   (`worktree.md`, «Ловушки»).
2. **Корень проекта**: каталог с `.claude/omixflow/flow.yaml`; в worktree это сам
   worktree, и команды сессии — по «Формы команд в изоляции» (`runtime.md`). Все пути
   агентам передаются абсолютными от него.
3. **Конфиг**: если `flow.yaml` нет, остановиться и предложить `/omixflow:doctor --init`.
   Значения читать через `cfg.py`, не парсить YAML в голове: ключ, которого нет
   в `flow.yaml`, `cfg.py` отдаёт умолчанием схемы (`--raw` — только конфиг).
4. **Адаптеры**: для каждого порта, который нужен фазе, получить цепочку и прочитать
   файлы в порядке вывода:
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.py" adapter tracker
   ```
   Какие порты нужны какой фазе:

   | Фаза | tracker | forge | lang | workspace |
   |---|---|---|---|---|
   | create, refine | да | | | |
   | start | да | | | да |
   | research | да | | да | да |
   | spec, plan | | | да | |
   | implement, review | | | да | да |
   | finalize | да | да | | да |
   | doctor | все | все | все | все |

   В research tracker нужен в режиме планировщика (блок и комментарии), workspace
   для кросс-репо ресёрча (research-worktree, `multitask.md`).

5. **Состояние**: `.tasks/{id}/state.yaml` через `state.py`. Резюм читает `phase`
   и `completed`, не угадывает по файлам. Адаптер tracker с возможностью `artifacts`:
   рабочая копия, публикация и восстановление по `protocol/artifacts.md`, «Хранение
   в задаче трекера».
6. **Диалог**: точки решения, их режимы и маршрут вопроса по `protocol/dialog.md`.
7. **Лид**: в состоянии задачи есть `lead` или `develop` запущен с `--lead` →
   прочитать `lead.md` «Доверие», «Сообщения», «Маршрут вопроса» (с «Порядок действий
   сессии»), «Регистрация», «Директива и пауза»: регистрация и вопросы в точках решения
   идут по ним в любом скиле, в том числе запущенном в новой сессии. После каждого
   `state.py finish` сессия шлёт лиду `notice` о пройденной фазе: после Start с веткой,
   базой, worktree, профилем и тиром, после Research с файлами Source Files Map.
8. **После сжатия контекста** сессия перечитывает «Сначала» своего скила заново и секции
   по условиям, которые уже наступили: сводка сжатия может потерять правило, которого
   больше нет перед глазами (AL-1175 дошёл до 921k).

**Команды без `cd`.** Харнесс сохраняет рабочий каталог между вызовами Bash: `cd` в одной
команде, даже внутри составной, уносит его для всех следующих. Скрипты плагина и адаптеров
ищут `flow.yaml` от текущего каталога (MEW-2: после `cd` в scratchpad скрипт трекера упал
«конфиг не найден»). Пути абсолютные, `git -C {путь}`, явные `--dir` в командах пакетных
менеджеров. Чем ещё опасен чужой каталог — `worktree.md`, «Ловушки». Сессия в worktree —
`runtime.md`, «Формы команд в изоляции».

## Формы команд в изоляции

Сессия, вызвавшая `EnterWorktree` (или получившая отказ «This session is isolated in the
worktree»), и её агенты: харнесс отклоняет команды, которые не может проверить. По отказам
прогонов 0.3–0.7, в порядке веса: переменная shell или `$(…)` в любой позиции (`R=…;
{команда} … $R`, `PATH=…:$PATH {команда}`, `python3 $S/…`, `$(date +%s)`); heredoc; `git -C`
не своего worktree (основное дерево, чужой worktree, `-C .`) — и одиночной командой; в
составной команде — скрипт через `bash`/`zsh`/`sh -c`, `cd`; устаревший алиас `complete` скрипта состояния
(только `finish`) и `git` как операнд другой команды. Обычные цепочки и конвейеры без этого проходят, разбивать их
не нужно: каждый лишний вызов — запрос с полным контекстом. Правила:

- пути литеральные и абсолютные — без `$VAR`, `$(…)` и `VAR=… команда`; `git -C` — только
  свой worktree, абсолютным путём;
- без heredoc — файлы пишут Edit и Write (журнал, артефакты; скрипты плагина пишут свои
  файлы сами); сообщение коммита длиннее строки — файл `{scratchpad}/commit-msg-{метка}.txt`
  через Write и `git -C {дерево} add {файлы} && git -C {дерево} commit -F {файл}` одним вызовом, не в
  `TASK_DIR` (он публикуется в карточку, T-11);
- цикл, вычисляемый аргумент, фоновый процесс кроме `gate.py start` — скрипт файлом в
  scratchpad (Write) и одна команда `zsh {путь}` или `python3 {путь}` целиком, не внутри
  составной; `python -c` — так же после отказа.

Файловые инструменты: отклоняются пути основного дерева (shared checkout); scratchpad
проходит. Журнал лида пишет только скрипт `lead.py` (`lead.md`, «Журнал»: номера записей под
блокировкой), не файловый инструмент. Текст отказа называет нужную форму («Split it into plain, separate
commands and run them from {worktree}»): следовать ему, не подбирать другую обёртку.
Агентам правило приходит строкой `ISOLATION` шаблона спавна («Спавн агентов»); в T-1
оркестратор вписывал его в промпт сам.

## Спавн агентов

Роли: researcher, architect, coder, tester, reviewer, web-fetcher. Агент берётся
по маппингу `agents` из конфига (`resolve.py agent {role}`): плагинный по умолчанию,
проектный при замене. Правила проекта к агенту (`.claude/omixflow/agents/{role}.md`)
передаются путём в промпте.

Агенты пайплайна — обычные субагенты Claude Code. Режим команд агентов
(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`) превращает именованных агентов в teammates — режим
для равных агентов, которые переписываются друг с другом. Пайплайну он не нужен и стоит
дорого: уведомления без usage, кэш промпта 5 минут на простое, `/resume` их не восстанавливает. Doctor предупреждает,
если режим включён; правила отчёта и ротации работают в обоих режимах.

**Адрес агента.** Architect, coder, tester и reviewer получают имя роли: `{role}-{id}` для
задачи, `{role}-{id}-{part}` для части, с ротационным суффиксом (`coder-{id}-2`). Имя
уходит в параметр `name` спавна, когда инструмент Agent харнесса его принимает, и всегда —
в начало `description`. С Claude Code 2.1.300 Agent параметра `name` не принимает
(Swarga AI Studio T-10: ни в одном `.meta.json` сессии имени нет; в T-8, T-9, T-11 на
2.1.296 — есть). **Адрес** — то, по чему агента находит SendMessage: имя, если харнесс его взял,
иначе `agentId` из результата спавна (строка `agentId: a17a5331e25a342a4 …`). Адрес
хранится в `state.yaml` (`state.py set TASK_DIR agents.{ключ}={адрес}`); agentId — служебный
(харнесс просит не показывать его разработчику): в log.md, ответах разработчику, лиду и
комментариях трекера агент называется именем роли. Дальше общение с агентом — SendMessage
по адресу (continuation, см. `review-cycle.md`). `agents.*`, записанные именем до обновления харнесса, читаются как
прежде: `agent_ctx.py` находит агента и по имени, и по id.
**После перезапуска сессии** (`claude respawn`; проверено на Swarga AI Studio T-7) агенты,
заспавненные до него, по имени не находятся («No agent named … is reachable»), а по id —
да. Агенту, которого оркестратор продолжает (`agents.*` в `state.yaml`, researcher,
ждущий ответа на `research-blocking`, tester при возврате задания), он шлёт сообщение
по `id` из `python3 {корень плагина}/scripts/agent_ctx.py {адрес}` (по имени: `others`
больше нуля — у имени были и прежние агенты, взят последний; адрес-id уже и есть id).
Адрес потерян — `agent_ctx.py --list`: агенты сессии с id, типом и `description` спавна.
Нет id или и по id не дошло — новый спавн с `PREVIOUS_REPORTS` и ротационным суффиксом,
`state.py set TASK_DIR agents.{ключ}={адрес}` и строка в log.md, как при ротации
(`tiers.md`): с ним пропадает контекст агента. После `/resume` с новым id сессии прежних
агентов нет — сразу новый спавн. В mewria MEW-25 сессия после `respawn` заспавнила агентов
заново, не пробуя id, и их контекст пропал.
**Researcher получает адрес, когда его продолжают**: каждый researcher, которого спавнит
скил `research` для задачи или части, получает имя (`researcher-{id}`,
`researcher-{id}-{part}`; синтез идёт под `researcher-{id}`) по правилу адреса и параметр
`CONTINUABLE: yes`. Researcher скила `create`, standalone `research "{тема}"`
и web-fetcher одноразовые, имя не обязательно.

Шаблон промпта:

```
Agent tool:
  subagent_type: "{агент по маппингу}"
  name: "{role}-{id}"                      # только когда Agent принимает name (до Claude Code 2.1.300)
  description: "{role}-{id}: {задание}"
  model: "{по protocol/tiers.md, если таблица задаёт}"
  prompt: |
    PROJECT_ROOT: {абсолютный путь}
    TASK_DIR: {абсолютный путь к .tasks/{id} или .tasks/{id}/{part}}
    ADAPTERS:
      lang: {пути цепочки lang, через запятую}
      workspace: {пути цепочки workspace}          # coder, reviewer
    RULES: {пути проектных правил агента или "none"}
    SPECS: {descriptions | adr {specs.adr_dir} | none}   # architect, coder, reviewer: `cfg.py get specs.mode` и `specs.adr_dir`; что сопровождает код при смене контракта (phases.md, SDD-инвариант)
    PARENT: the orchestrator of this session. Report only to it, once per turn: with
      SendMessage when you have that tool, then end your turn with the single line `sent`,
      never a second summary; without SendMessage, or when the send fails, your final
      reply is the reply your output format prescribes: the short summary when the full
      report goes to a file, written before the summary; the whole report only when the
      format names no file or the harness refused that file (your output format says how).
      A path in your reply starts with a path given in this prompt (PROJECT_ROOT,
      TASK_DIR, REPORT_PATH, FINDINGS_PATH), never with one you rebuild.
      The harness may label it team-lead; it is not the OMIXFlow lead session: never
      message the lead, never call your parent "lead".
    PLUGIN_ROOT: {абсолютный корень плагина}             # coder, tester, reviewer: долгие гейты; tester: рецепт пробы
    REPORT_PATH: {TASK_DIR}/reports/{phase}-{метка}.md   # coder, tester
    SCRATCH_DIR: {scratchpad оркестратора}/{имя агента}   # coder, tester, reviewer, researcher
    ISOLATION: this session is isolated in its worktree; the harness refuses what it
      cannot verify. Use literal absolute paths (no shell variables, no `$(…)`, no `VAR=…
      command`), no heredoc, `git -C` only on this worktree by absolute path, no `cd`; a
      loop, a computed argument or a background process other than `gate.py start` is a
      script written into SCRATCH_DIR with Write and run as the whole command. The
      refusal text names the form to use: follow it.   # сессия, вызвавшая EnterWorktree; агенты с Bash
    {параметры режима агента: MODE, STEP, ASPECTS, ARTIFACT_PATHS, FINDINGS_PATH, ...}
```

Агент читает адаптеры сам: из них он узнаёт гейты, конвенции тестов, запрещённые
подавления и инструменты навигации. В промпте инструменты не перечисляются, а правила
адаптеров и проекта не пересказываются: только путь и раздел. Пересказ сужает или
расширяет правило: «no diagnostic suppressions» в промпте остановило coder'а на
обоснованном подавлении, которое адаптер разрешает.

`PARENT` одной строкой и в кросс-репо спавне: в режиме команд агентов харнесс показывает
родителя субагента как `team-lead`, и в сессии под лидом агенты путали его с сессией лида
(`lead.md`, «Роли»: агенты лиду не пишут).

В worktree все пути абсолютные внутри worktree, с явным запретом читать основное
дерево (`protocol/worktree.md`), и у сессии, вызвавшей `EnterWorktree` (или получившей
отказ «This session is isolated in the worktree»), строка `ISOLATION` — рецепт форм команд
(`runtime.md`, «Формы команд в изоляции»); без неё в T-1 оркестратор и агенты обходили
отказы наугад. Фоновая сессия в основном дереве (`bgIsolation: none`) не изолирована.

Параметры researcher (все необязательные):

| Параметр | Значение |
|---|---|
| `MODE` | `task` (дефолт) или `synthesis`: сводный research.md мультизадачи по отчётам частей |
| `REPO` | `{name} ref={ref} sha={sha}` для части в чужом репозитории |
| `INPUTS` | абсолютные пути research.md частей-зависимостей (в синтезе всех частей) |
| `HANDOFF` | `required`, если от части зависят другие, иначе `optional` |
| `ANSWERS` | уже отвеченные блокирующие вопросы при перезапуске |
| `CONTINUABLE` | `yes` только у именованного спавна скила `research`; иначе `no` |
| `PARTS_IN_FLIGHT` | файлы незавершённых частей; только в мутирующих профилях |

Кросс-репо спавн (часть с `repo` из `workspace.repos`):

```
Agent tool:
  subagent_type: "{агент researcher домашнего проекта}"
  name: "researcher-{id}-{part}"           # по правилу адреса
  description: "researcher-{id}-{part}: {задание}"
  model: "{models.strong}"
  prompt: |
    PROJECT_ROOT: {абсолютный корень чужого репозитория или его research-worktree; только чтение}
    TASK_DIR: {абсолютный путь к .tasks/{id}/{part} в домашнем проекте}
    ADAPTERS:
      lang: {resolve.py adapter lang --project {чужой} --fallback-project {домашний}}
    RULES: {resolve.py agent researcher --project {чужой} --fallback-project {домашний}}
    REPO: {name} ref={ref} sha={sha}
    CONTINUABLE: yes
    PARENT: {как в основном шаблоне}
    SCRATCH_DIR: {как в основном шаблоне}
    {INPUTS, HANDOFF, ANSWERS}
```

Агент берётся из домашнего проекта (сессия регистрирует только его агентов),
правила из чужого репозитория. Пишет агент только в `TASK_DIR` и `SCRATCH_DIR`.

## Отчёт агента

Полный отчёт агент пишет в файл внутри `TASK_DIR`, а отвечает сводкой не длиннее
10 строк с путём: длинный ответ обрезается в канале сообщений, и хвост отчёта
приходится добирать сообщениями. Файл по роли: coder и tester — `REPORT_PATH`,
reviewer — `FINDINGS_PATH` (`review-cycle.md`), researcher — `research.md`, architect —
свои артефакты. Каждое задание получает свой путь `{TASK_DIR}/reports/{phase}-{метка}.md`,
где `{phase}` — фаза скила, давшего задание (implement, review, finalize), а метка:

| Метка | Задание |
|---|---|
| `step{N}` | шаг плана N |
| `tests-step{N}` | тесты tester'а к шагу N |
| `fix-pass{N}` | пакет фиксов после прохода ревью N |
| `tests-pass{N}` | тесты tester'а в пакете фиксов прохода N |
| `sync{K}` | разрешение конфликтов K-й синхронизации с базой (K — следующий номер в `syncs` состояния) |
| `sync-fix{K}` | поломки вне конфликтов после K-й синхронизации |
| `spec-sync-pass{N}` | строки спецификаций, называющие новые тесты tester'а прохода N, когда coder уже чинил код в этом проходе |
| `gate-fix{K}` | K-я починка красного гейта вне шага плана и вне пакета фиксов прохода, в том числе проверки, которую оркестратор выполняет сам |
| `tests-gate-fix{K}` | тесты tester'а в K-й починке красного гейта |

Путь приходит в спавне или в сообщении задания. Оркестратор читает файл, а не ответ;
`reports/` входит в артефакты задачи наравне с `review/` (`artifacts.md`). Путь в ответе
агента — не источник: оркестратор читает по своим параметрам. В T-9 architect правил
spec.md в worktree, а в ответе назвал путь основного дерева. Отчёт coder'а и tester'а
сверяет `scripts/report.py check` против дерева и логов гейтов (разделы, `TREE STATE`,
`MUTATIONS`, гейты набора, `BYTES CHECK`, `SCRATCH`): оркестратор получает вердикт в пять
строк и при коде 1 отправляет агенту готовый текст из вывода; отчёт на 10–30k он не читает.

**Временные файлы агента** — пробы, эксперименты, клоны, сборки вне задачи — только
в `SCRATCH_DIR` из шаблона спавна: `{scratchpad оркестратора}/{имя агента}`. Имя агента
уникально (у части — с `-{part}`, «Спавн агентов»), каталог один на все его задания,
внутри — подкаталог на метку отчёта; в голый `/tmp` и в дерево проекта — нельзя. Агент
убирает их сам. Если команду удаления запретили, другую форму удаления он не подбирает:
оставляет и называет строкой `SCRATCH: {путь} {размер}` в отчёте (у reviewer'а
и researcher'а — в ответе). Оркестратор любой фазы переносит её в log.md строкой
`- SCRATCH {метка}: {путь} {размер}`; итог Finalize и `done` лиду (поле `scratch`)
называют остаток разработчику. В MEW-17 пробы агентов в `/tmp` — 118 МБ — остались,
удалить их агентам не дали.

**Харнесс и файл отчёта.** Харнесс Claude Code пишет в системный промпт каждого субагента
заметку «Do NOT Write report/summary/findings/analysis .md files. Return findings directly
as your final assistant message…» (в транскриптах — с 2.1.267) и отклоняет Write субагента
в `.md`-файл с «report» в имени («Subagents should return findings as text, not write report
files»). Заметка исходит из того, что родитель читает только ответ, а здесь файл отчёта —
артефакт задачи: он коммитится с ней, его читают оркестратор и сменщик агента
(`PREVIOUS_REPORTS`). Поэтому coder, tester, reviewer (`FINDINGS_PATH`) и researcher
(`research.md`) знают, что заметка не касается их файла, а прочие файлы отчётов — касается.
В T-6 tester послушался заметки и ответил полным текстом без файла; остальные агенты
прогонов на 0.5.0–0.6.1 файл писали. Отказ по имени: в T-5 отклонены все четыре `.md`-куска
отчёта coder'а в scratchpad (`report2-head.md`, `report-tail.md`), а `report-head.txt`
и `report-tail.txt` сразу после них прошли, как и записи в `reports/{phase}-{метка}.md` —
«report» там только в имени каталога. Правило харнесса не документировано, это наблюдение;
поэтому с запасом временный файл и кусок отчёта не называются `report*`, а ни метки
таблицы, ни имена файлов `REPORT_PATH` и `FINDINGS_PATH` слова «report» не содержат.

**Отказ записи.** Если харнесс отклонил Write по `REPORT_PATH`, агент не обходит отказ
другим именем или через shell, а отвечает полным отчётом с первой строкой `REPORT_PATH
refused by the harness: {сообщение харнесса}`. Такой ответ — отчёт. Оркестратор проверяет,
что он дошёл целиком (есть последний раздел формата: у coder'а `NOTES`, у tester'а
`SUMMARY`), иначе просит остаток сообщением; затем пишет в `REPORT_PATH` ответ целиком, с
первой строкой (`report.py check` узнаёт её и называет в вердикте), а в log.md — «отчёт
{метка} записан оркестратором: {сообщение харнесса}».

**Один отчёт за ход.** Сводку агент шлёт один раз: SendMessage и строка `sent` в конце
хода, а без SendMessage или при сбое отправки — итоговым ответом (строка `PARENT`
шаблона). Если формат вывода агента называет файл, итоговый ответ — та же сводка, а файл
пишется до неё при любом канале; целиком отвечает только агент, чей формат файла не
называет (researcher с `OUTPUT: inline`), или агент, которому харнесс отказал в записи
`REPORT_PATH` («Отказ записи»). В T-1 tester без SendMessage ответил полным
текстом и файл по `REPORT_PATH` не записал; строка `PARENT` тогда называла итоговый ответ
отчётом. В режиме команд агентов итоговый текст тоже доходит до оркестратора — `result`
уведомления о простое; в MEW-2 агенты писали после сводки ещё и итог втрое длиннее,
и каждый отчёт приходил дважды. Уведомление с `sent` — конец хода, не новый отчёт;
сводка в уведомлении бывает только у агента, который не отправил её сообщением.

**Одно задание за раз.** Сообщение агенту, который ещё работает, доходит до него только
после конца хода: в MEW-2 оба дополнения пришли агентам после их отчёта, а оркестратор
принял отчёт без дополнения за потерю и повторил его. Новое задание или дополнение живому
агенту уходит после его отчёта на текущее; решение, пришедшее раньше, ждёт. Если сообщение
уже ушло, отчёт без него — не потеря: ответ придёт следующим ходом, повторять нельзя.

**Ответ без итогов — не отчёт.** Агент отчитывается, когда все запущенные им команды
закончились. Ответ `done`, в котором гейт ещё идёт («жду фоновые гейты», нет кода
выхода), или без файла по `REPORT_PATH` (кроме ответа `REPORT_PATH refused by the harness`,
«Отказ записи» выше) оркестратор сразу возвращает агенту сообщением:
дождаться завершения и отчитаться. Ждать продолжения бесполезно: ход агента закончился,
и окончание фоновой команды его не разбудит. Остановка с причиной (`STATUS: stopped`:
решение по дизайну, конфликт spec и plan) — законный ответ без гейтов: `GATES: not run —
{причина}`.

**Обрыв сбоем.** Уведомление `failed` (сбой API, сеть) без файла отчёта (`REPORT_PATH`,
`FINDINGS_PATH`, `research.md`) — повтор того же задания тому же агенту (по адресу, после
перезапуска сессии — по id) с теми же путями и строкой «прошлое задание оборвано сбоем —
сверь дерево и продолжи». Так же — задание, оборванное остановкой сессии: после `respawn`
уведомления `failed` нет, и файла отчёта нет. Это не новый проход ревью и не попытка в счёт
`limits.*`, решения лида оно не требует. Второй `failed` на то же задание — СТОП, вопрос
в точке `deadlock`: сбой сети не лечится новым агентом, поэтому это не stall, после
которого implement берёт нового. В T-7 reviewer оборвался на ENOTFOUND до записи
`FINDINGS_PATH`, и повтор тем же заданием прошёл.

## Модели

`model` при спавне берётся из таблицы `protocol/tiers.md`; имена сильной
и облегчённой модели в конфиге `models.strong` и `models.light`. Пустая ячейка
таблицы означает значение из фронтматтера агента.

## Гейты

Скилы и агенты называют гейты по именам порта lang: typecheck, test, lint, structure,
build, e2e, visual. Команду и критерий даёт адаптер и конфиг `verify.*`. Долгие гейты (`background: true`
в `verify.*` или раздел `long_running` адаптера lang) запускаются отсоединённо и ждутся
одним долгим опросом (`--timeout 540` при таймауте Bash 600000 мс; шесть опросов по 100 с —
шесть запросов с полным контекстом, цикл shell вокруг `poll` ставил фоновую сессию на запрос
разрешения, G-56): `scripts/gate.py start {имя} --root {корень} -- '{команда}'`, затем
`gate.py poll {имя} --root {корень}` до `EXIT` (`LOST` — процесс гейта умер, запустить
заново). Вывод и код выхода лежат в git-каталоге дерева: не попадают
ни в коммит, ни в публикацию артефактов. Имя выводится, а не придумывается: у агента —
`{метка}-{gate}`, где метка — имя файла его отчёта без расширения (`REPORT_PATH`,
у reviewer'а `FINDINGS_PATH`): `implement-step3-build`, `review-sync1-build`,
`review-pass2-e2e`; у оркестратора — `{moment}-{gate}` по моменту `resolve.py verify --at`
(`review-build`, `delivery-build`, `accept-e2e`, приёмка лида тоже), фоновая проверка
оркестратора — `{moment}-check-{имя}`: имя проверки может совпасть с именем гейта. Метки уникальны на задание («Отчёт агента»),
повторный запуск того же имени заменяет прежний прогон (`gate.py` снимает идущий).
Агент называет имя в строке гейта отчёта: в T-3 coder в синхронизации назвал гейт сам
и не написал имени, и `gate.py poll build` оркестратора не нашёл лога. Один вызов скрипта с литеральными путями
проходит изолированную worktree-сессию, цикл shell с `$?` — нет. Ответ агента, пока его
гейт идёт, — не отчёт («Отчёт агента»). Набор гейтов шага (с гейтами «Test checkpoint»
шага, `--also`) обязателен перед коммитом шага и пакета фиксов, полный — на Review,
при синхронизации с базой, перед сдачей и на приёмке лида. Какие гейты входят в набор
сейчас, отдаёт `scripts/resolve.py verify --at {step|review|delivery|accept}`
(для review и delivery с `--task TASK_DIR`); сами наборы и `when` определяет порт lang,
«Гейты».

## Проверки оркестратора

Проверки, которые оркестратор выполняет сам (порт lang, «Проверки оркестратора»), идут
в тех же точках, что наборы гейтов: скил называет момент, `resolve.py verify` отдаёт
`checks`, и каждая выполняется по своему подразделу адаптера; пустой список — проверок
нет. Проверки по требованию (`on_demand`) — когда их требуют task.md, spec или plan.

- **Порядок.** После зелёных гейтов агента и сверки его отчёта, до коммита: шаг или
  пакет фиксов с красной проверкой не коммитится.
- **Красная.** Дефект кода уходит coder'у продолжением задания в счёт
  `limits.coder_iterations`, дефект только в тестах — tester'у; после фикса — гейты
  и та же проверка заново.
- **Ресурс разработчика.** Проверке он нужен — вопрос в точке `lang.window`, как только
  известно, что проверка понадобится (до её момента; под лидом `nowait`). «Позже» — работа
  идёт до момента проверки и там ждёт окна; «без проверки» — строка «не проверено» в log.md.
- **Проверить нельзя** (инструмент не отвечает, среда недоступна): не коммитить молча,
  точка `deadlock` с вариантами из адаптера.
- **След.** Строка в log.md по формату адаптера, в секции шага или фазы. После зелёного
  прогона в моменты `review` и `delivery` — `state.py set TASK_DIR checks.{имя}={полный sha
  HEAD}`: на сдаче проверка не повторяется, если после этого коммита её области не менялись
  (незакоммиченное на момент записи считается изменением — прогон повторится).
- **Долгая** (`background: true`) — отсоединённо, как долгий гейт.

## Стоимость

Стоимость фазы считает `scripts/cost.py` по транскриптам сессии и её субагентов: запросы,
средний контекст, доли ролей, перестройки кэша, отказы изоляции, опросы гейтов; в условных
«входных токенах Opus» (cost_eq: input 1, cache write 1,25, cache read 0,1, output 5; модели
дешевле — с коэффициентом из `cost-state` сессии). Это сравнительная мера, не счёт; правило,
которое она показывает: cost ≈ 0,1 × Σ(контекст каждого запроса) плюс output (по прогонам
0.7 — 16–19 %). Окно фазы — время с прошлого вызова: `cost.py phase` ведёт `cost.last`
и `cost.phases` в state.yaml, скилы их не правят.

- **Start** вызывает `python3 {корень плагина}/scripts/cost.py phase TASK_DIR start` сразу
  после `state.py finish … start` (запись `start` = Refine и Start от начала сессии): с него
  окна следующих фаз начинаются с задачи, а не с начала сессии.
- **Research, Spec, Plan, Implement, Review, Finalize** вызывают `cost.py phase TASK_DIR {phase}`
  перед своим `state.py finish` и переносят напечатанную строку `- Стоимость: …` в секцию
  фазы log.md. В S и M spec и plan закрываются одним вызовом `spec`.
- **Мультизадача** на своём Start вызывает `cost.py phase TASK_DIR start` так же.
  **Часть** с `part_runner: sequential` — как задача, со своим `PART_DIR`: её окно
  начинается с самого позднего курсора среди неё, мультизадачи и сестринских частей,
  записанных этой же сессией (части идут по очереди в одной сессии), так что прежние
  части не считаются повторно; курсор части другого владельца не учитывается. Две
  активные части одного владельца в одной сессии (`parallel_per_owner` больше 1) курсоров
  друг друга до интеграции не видят, их окна перекрываются — известный предел.
  Части планировщика (`part_runner: scheduler`) идут параллельно в одной сессии, их
  стоимость не разделить: части `cost.py` не вызывают, мультизадача вызывает `research`
  на синтезе и `finalize` на своём Finalize. Finalize мультизадачи складывает `cost.total_eq`
  частей `sequential` в итог.
- Итог Finalize называет `cost.total_eq` state.yaml и фазы по убыванию — после вызова
  `cost.py phase … finalize`, иначе итог не включит Finalize. Сессия без транскрипта
  (код 3) — строка «стоимость неизвестна: {причина}», фаза идёт дальше.

## Внешние действия

Запись в трекер, ветвление, PR, смена статуса: только через возможности адаптера
и только с подтверждением по `dialog.md`. Оркестратор не вызывает инструменты
трекера или хостинга «в обход» адаптера.

## Режим запуска

`state.yaml` хранит `mode`: `pipeline`, когда фазу ведёт `develop`, или `manual`
при standalone-запуске фазового скила. В `pipeline` фазовый скил не печатает
«следующий шаг» и не ждёт подтверждения перехода: это делает `develop`.
