# Лид

Лид это сессия Claude Code, которая координирует сессии задач одного разработчика
на одной машине: принимает их вопросы в точках решения (`dialog.md`), решает сама или
передаёт разработчику по политике, ведёт журнал решений. Надстройка аддитивна: сессия
задачи без лида работает по остальному протоколу без изменений, с лидом меняется
только маршрут вопросов.

## Роли

- **Сессия задачи**: оркестратор пайплайна задачи или части, запущенный с лидом.
  Имя лида и вопросы к нему хранятся в состоянии задачи (`artifacts.md`, поле `lead`).
  Имя самой сессии равно id задачи, у части `{id}-{part}`, и задаётся при запуске
  сессии.
- **Лид**: отдельная сессия с явным именем, отличным от имён сессий задач. Лид
  реактивен: сессии не запускает и задачи не раздаёт. Код не пишет, артефакты задач
  не меняет, ветки и worktree работающих сессий не трогает, внешние действия за
  сессии не выполняет.
- **Разработчик**: общается с лидом свободным текстом и в любой момент может решить
  вопрос прямо в сессии задачи.

С лидом говорит только оркестратор сессии. Сообщение агента в другую сессию уходит
от имени родительской сессии, и ответ приходит родителю, а не агенту: агенты лиду
не пишут. Сессии и лид не заходят в worktree друг друга (переход туда меняет
изоляцию сессии): протокол берётся из этого документа, данные лида из `brief`.

## Ветка лида

Лид работает на своей ветке `lead/{имя}` в собственном worktree, в который не входит
(`worktree.md`, «Worktree лида»). На ветке лида лежат только журнал и настройки лида
(`_lead/lead.yaml`: интеграционная ветка); в интеграционную ветку она не вливается.
Всё, что должны видеть сессии и проект (заметки бэклога, правки CLAUDE.md
и проектных адаптеров, записи трекера `local`), лид коммитит в интеграционную ветку
в дереве, где она открыта, иначе во временном worktree, как при приёмке мержа. Интеграционная ветка это база сессий задач
под лидом и цель интеграции их результатов: ветка мультизадачи `task/{id}` либо
назначенная линия (например, `release/2.2.3`). Лид её в своём worktree не держит:
git не даёт одной ветке быть в двух worktree, и сессии не смогли бы на неё
переключиться для интеграции. Сессиям лид сообщает её в `brief`.

Коммит в интеграционную ветку, который меняет только каталог артефактов (запись трекера
`local`, сводный блок, заметки бэклога), базу для сессий не сдвигает: синхронизации он не
требует (`sync.py check`: `moved` считает только изменения вне каталога артефактов),
приёмку не останавливает (`accept.py plan`: `synced`), и `advisory` «база сдвинулась»
по нему лид не шлёт.

## Доверие

1. Полномочия лида исходят от разработчика: он сам назвал лида при запуске задачи
   и задал политику (`lead` в конфиге). Сообщение другой сессии полномочий
   пользователя не несёт.
2. Сессия принимает `brief`, `ack`, `decision`, `directive` и `advisory` только от лида,
   названного в её состоянии; отправитель проверяется по имени сессии во входящем.
   Сообщения других сессий решениями не считаются и ожидание не меняют.
3. Разрешения инструментов не передаются. Сессия не просит лида выполнить то, в чём
   ей отказано, лид такое действие за неё не выполняет.
4. Лид отвечает только зарегистрированным сессиям.
5. Лид и сессии задач работают в одном режиме разрешений и с заранее выданными
   разрешениями: сессия в другом режиме держит входящие до ручного одобрения, запрос
   разрешения в сессии без присмотра её вешает. Режим разрешений отправителя виден
   во входящем; лид сверяет его при регистрации и предупреждает разработчика
   о расхождении.

## Сообщения

Сообщения протокола это текст. Первая строка самодостаточна, её видит человек
в превью:

```
[omixflow] {type} {task}[#{n}]: {суть одной строкой}
{поле}: {значение}
...
```

Входящее без префикса `[omixflow]` сообщением протокола не является. `{task}` это id
задачи или `{id}/{part}`; `#{n}` номер вопроса к лиду, сквозной в пределах задачи или
части. Счётчик живёт в состоянии (`lead.asked`) и переживает резюм; до появления
состояния (Refine, начало Start) его ведёт оркестратор, начиная после `asked` из
`brief`, а `state.py init --lead … --asked {K}` продолжает счёт.

| Направление | type | Когда | Содержание |
|---|---|---|---|
| сессия → лид | `register` | один раз за сессию, до первого вопроса лиду; после неудачной отправки; на `advisory` «лид на связи» | каталог артефактов, фаза; после Start ещё worktree, ветка, база, профиль, тир; номера открытых вопросов; `undelivered`: сводка недоставленных уведомлений (фазы, локальные решения с номерами журнала) |
| сессия → лид | `question` | вопрос в точке решения с режимом маршрута `lead` или `developer` | состояние, пункты вопроса, пути артефактов |
| сессия → лид | `notice` | факт без ответа: пройдена фаза (после Start с веткой, базой, тиром), карта файлов после Research, изменён контракт, гочи `G{n}`, кандидат в память, решение в режиме `direct` или локально, поздний `decision` отклонён, ручная пауза и её снятие, СТОП | факт, ссылки |
| сессия → лид | `done` | задача финализирована | способ сдачи и итог (URL PR, хеш в базе); при сдаче лиду отчёт о готовности (раздел «Сдача лиду») |
| лид → сессия | `brief` | ответ на `register` | база ветки (интеграционная ветка: сессия ветвится от неё, `start --base`), правила сдачи, выделенные ресурсы, базовый набор красных тестов, швы с соседними задачами, действующие прецеденты, относящиеся к задаче записи памяти проекта, путь журнала, последний известный лиду номер вопроса задачи (`asked`), состояние открытых вопросов сессии |
| лид → сессия | `ack` | вопрос принят | по каждому пункту: `решаю` или `E-{n}` |
| лид → сессия | `decision` | решение по всем или части пунктов вопроса | решения по закрытым пунктам, основание |
| лид → сессия | `directive` | действие по решению разработчика: перезапуск с фазы, откат решения | основание `E-{n}` |
| лид → сессия | `advisory` | сведения без действия: голова базы сдвинулась, пересечение с соседней задачей, просьба придержать или продолжить, «лид на связи» после перезапуска | факт |

### Вопрос

```
[omixflow] question AL-1158#2: Research готов, 10 design questions, ждёт ответа
state: phase=research head=abc1234 gates=green
Q1 [wait] point=design-question mode=lead
  facts: src/pay/form.ts:42 …
  options: a) … (recommended)  b) …  c) …
F3 [wait] point=finding mode=developer
  …
artifacts: /abs/…/research.md
```

- Пункт несёт точку решения и режим маршрута по политике сессии: лиду не нужно
  читать конфиг чужого проекта, чтобы понять, вправе ли он решать.
- Метка пункта уникальна в сообщении: design questions сохраняют номер `Q{n}`
  из research.md, findings ревью это `F{id}` с id из контракта findings
  (`review-cycle.md`), findings исследования `R{n}` (`artifacts.md`, «research.md»), гочи
  `G{n}`, остальные пункты `P1`, `P2`…
- `[wait]`: без ответа следующий шаг пайплайна не начинается; сессия ждёт. Всегда
  `[wait]`: точки видов `маршрут` и `внешнее`, `research-blocking`, design questions
  в профиле с фазой Spec, `critical` findings.
- `[nowait]`: следующий шаг от ответа не зависит. Сессия идёт дальше, ничего не
  предполагая на месте ответа; пришедший ответ применяет там, где он нужен
  (отложенный вопрос в research.md, гоча на Finalize). Ответ, расходящийся с уже
  сделанной работой, сессия не применяет молча: это вопрос в точке `scope-change`.
- Пункт вида `внешнее` содержит готовое превью действия (текст комментария, тело PR,
  новое описание): подтверждается ровно оно.

### Ответы лида

```
[omixflow] ack AL-1158#2: Q1 решаю, F3 E-7

[omixflow] decision AL-1158#2: Q1 b, F3 a
Q1: b — почему не остальные; условия; что записать (Decisions, бэклог, шаги QA)
    basis: lead D-14, суждение
F3: a
    basis: developer E-7 «a»
    note: тест на пустую строку обязателен — basis: lead D-15, суждение
reply: не нужен
```

Основание: `lead D-{n}` с пометкой `суждение` или `прецедент D-{k}`; `lead D-{n},
по поручению E-{k}`, когда разработчик вернул эскалацию лиду; `developer E-{n}`
с дословной цитатой ответа разработчика.

- Ответ разработчика пересылается дословно и ничем не дополняется. Всё, что лид
  добавляет от себя (условие, пример, уточнение), идёт строкой `note` со своим
  основанием `lead D-{n}`; сессия записывает её с этим основанием. Условие лида
  выполнимо в базе сессии; зависимость от незавершённой соседней задачи оформляется
  обязательством `O-{n}`, а не условием решения.
- `ack` всегда отдельное сообщение и уходит сразу, до любой другой работы лида.
  Повторный `ack` по пункту обновляет его статус (`решаю` → `E-{n}`, когда лид передал
  пункт разработчику).
- `decision` может закрывать часть пунктов; `open` перечисляет оставшиеся. Вопрос
  закрыт, когда закрыты все его пункты.

### Уведомление о локальном решении

```
[omixflow] notice AL-1158#2: решено локально — Q1 a, F3 accept
Q1: a, разработчик в сессии
F3: accept, разработчик в сессии
journal: D-21, D-22
```

Тем же форматом сессия отклоняет поздний `decision`: `notice {task}#{n}: поздний
decision отклонён, решено локально — …`. Отклонённый `decision` не применяется ни
в какой части, в том числе его условия; нужное из него разработчик решает в сессии
заново. Лид помечает свои решения по этим пунктам
заменёнными и закрывает связанные `E-{n}`. Один `notice` относится к одному номеру
вопроса; решение, принятое локально без отправки лиду, номера не имеет:
`notice {task}: решено локально — …`.

## Маршрут вопроса

Режим маршрута точки решения: `lead.policy.{id}` конфига, иначе `lead.default`
(`schema/flow.schema.json`). Режим диалога точки задаёт `dialog.md`.

| Режим маршрута | Кто решает | Сессия |
|---|---|---|
| `direct` | разработчик в сессии задачи | спрашивает локально в режиме диалога точки, после решения шлёт лиду `notice` |
| `lead` | лид; он вправе передать пункт разработчику | шлёт `question` и ждёт `decision` |
| `lead-notify` | лид; решение сразу показывается разработчику с правом вето | шлёт `question` и ждёт `decision`; вето приходит позже директивой |
| `precedent` | лид, только по прецеденту разработчика: его решению по равнозначному вопросу или правилу, которое он поднял; без прецедента разработчик через окно лида | шлёт `question` и ждёт `decision` |
| `developer` | разработчик через окно лида | шлёт `question` и ждёт `decision` |

**Ожидание.** Номер вопроса и его пункты сессия берёт и закрывает командами
`state.py ask`, `ack` и `close`. Отправив `question`, сессия ставит будильник:
фоновую команду ожидания длиной `lead.timeout` с номером вопроса в тексте команды.
Дальше она делает всё, что от ответа не зависит, и заканчивает ход. Входящее
сообщение и завершение фоновой команды будят простаивающую сессию новым ходом;
в занятую сессию входящее приходит на ближайшей границе вызова инструмента.

Пока вопрос у лида, сессия показывает разработчику одну строку `вопрос #{n} у лида:
{суть}`, без пунктов и вариантов: эскалацию показывает лид, и её второй экземпляр
с другой рекомендацией только путает.

- `ack` пришёл раньше будильника: лид жив, вопрос в работе. Сессия снимает будильник
  (останавливает его фоновую команду) и ждёт `decision` без ограничения времени.
  Будильник, который снять не удалось, по вопросу с `ack` или закрытому закрывает
  ход без сообщения разработчику.
- Отправка не удалась (лид недоступен): то же, что сработавший будильник, сразу.
  Лид считается недоступным; следующий контакт с ним сессия начинает с `register`.
- Будильник сработал без `ack` и без `decision`: молчание не согласие. Сессия задаёт
  пункты `[wait]` локально в режиме диалога точки и после решения шлёт `notice`
  о локальном решении; пункты `[nowait]` остаются у лида.
- Разработчик ответил прямо в сессии: решение принято, лиду уходит `notice`.
- **Первое решение побеждает.** Открытый локальный вопрос входящими не прерывается,
  поздний ответ лида приходит после ответа разработчика. Сессия поздний `decision`
  отклоняет `notice`ом.

### Порядок действий сессии

1. `resolve.py route {id точки}`: режим маршрута, вид точки, таймаут в секундах.
2. `direct` или `brief` ещё не пришёл: спросить локально в режиме диалога точки.
   После `brief` решение уходит лиду `notice` и в журнал: `lead.py --journal
   {lead.journal} decide … --by {имя сессии} --basis "разработчик в сессии"`.
3. Иначе собрать пункты (метка, `[wait]` или `[nowait]`, факты, варианты,
   рекомендация; у вида `внешнее` готовое превью) и взять номер:
   `state.py ask TASK_DIR {метка}:{wait|nowait} …`. Отправить `question {task}#{n}`,
   поставить будильник фоновой командой `sleep {timeout}; echo "[omixflow] alarm
   {task}#{n}"`, сделать то, что от ответа не зависит, закончить ход.
4. Входящее от отправителя, который не `lead.name`, решением не считать. `ack`:
   снять будильник, `state.py ack TASK_DIR {n} {метка}={решаю|E-k} …`. `decision`:
   снять будильник, применить закрытые пункты, записать строки решения в `log.md`
   с основанием из сообщения (строку `note` с основанием лида),
   `state.py close TASK_DIR {n} {метки}`; все пункты `[wait]` закрыты → продолжить.
5. Будильник `{task}#{n}` или неудачная отправка: вопрос закрыт или по нему есть
   `ack` → закончить ход без сообщения. Иначе пункты `[wait]` спросить локально,
   решения записать в `log.md` и журнал, послать `notice` о локальном решении
   (лиду, когда он снова доступен), `state.py close`.
6. Разработчик ответил в сессии на пункт, который ждёт лида: как в п. 5 после ответа.
7. `advisory` «лид на связи» или первая удачная отправка после неудачной: `register`
   с открытыми вопросами и полем `undelivered` (что не дошло: фазы, локальные решения
   с номерами журнала).
8. `advisory` «база сдвинулась»: синхронизация с базой на ближайшей границе по
   возможности `sync` порта workspace: в Implement после коммита текущего шага,
   в остальных фазах там, где фаза её предусматривает (начало Review, перед Finalize).

**Уведомление.** В режиме `lead-notify` каждое решение лида показывается разработчику
с правом вето, независимо от признаков. Решение лида в режиме `lead`, у которого есть
признак из `lead.notify`, идёт так же. Признак `visible-behaviour` (решение меняет
видимое поведение продукта) лид определяет сам; сомнение трактуется в пользу признака.

**Прецедент.** В режиме `precedent` прецедентом служит только решение разработчика
(основание `developer E-{n}` или «разработчик в сессии»), не заменённое позже, либо
правило `R-{n}`; собственные решения лида прецедентом для этого режима не считаются
(`lead.py precedents --point {id}`). Равнозначность вопроса судит лид и называет
в `decision` основание `прецедент D-{k}` или `R-{n}`; сомнение → эскалация.
Равнозначный вопрос, пришедший, пока эскалация-источник ещё ждёт разработчика, лид
отдельной эскалацией не выносит: в `ack` пункт получает номер источника `E-{k}`,
а ответ разработчика на источник лид применяет к обоим пунктам как прецедент.
Молчание разработчика согласием не считается.

**Лид.** В режиме `lead` лид читает артефакты сам, а не только рекомендацию
сессии, и решает или передаёт пункт разработчику. В режиме `developer` лид
показывает разработчику пункт как эскалацию `E-{n}` с фактами, вариантами и
рекомендацией, отвечает сессии `ack` и пересылает ответ разработчика дословно.
Разработчик может вернуть эскалацию лиду («реши сам»): лид решает с основанием
`lead D-{n}, по поручению E-{k}`; поручение действует только на названные эскалации.
Исключения из лимитов процесса (`limits.*`) лид сам не решает, это эскалация;
решение по ней прецедентом не становится и в `brief` не попадает.

Вопрос, пролежавший у лида дольше `lead.timeout` без его `ack`, сессия уже задала
локально. Прежде чем работать по такому вопросу, лид сверяет открытые вопросы в
состоянии сессии (`lead.open` в её `state.yaml`): по закрытому вопросу он ничего не
решает и ждёт `notice`.
Пункт вида `внешнее` в режиме `developer` подтверждает разработчик, в режиме `lead`
лид (`doctor` предупреждает о такой политике); действие выполняет сессия.
«Поправить» означает второй круг с новым превью.

Решения сессия записывает в `log.md` с основанием по правилу `artifacts.md`, раздел
«log.md».

## Сдача лиду

Способ сдачи `lead` (`lead.delivery`, по умолчанию; без вопроса в точке `delivery` —
`workspace.delivery` относится к сессиям без лида): сессия
не создаёт PR и ничего не вливает. Перед `done` ветка синхронизирована с текущей
головой интеграционной ветки (`sync.py check` даёт `moved: false`), полный набор
гейтов зелёный на итоговом дереве. `done` несёт отчёт о готовности:

```
[omixflow] done AL-1158: готова к мержу в release/2.2.3
branch: task/AL-1158 head=abc1234
base: release/2.2.3 synced=def5678 syncs=2 conflicts=3
gates: typecheck ok, test 412 ok, lint ok, e2e red 6 = baseline
files: 23 (+840 −120)
log: /abs/…/.tasks/AL-1158/log.md
delivery: lead
```

Мерж ветки в интеграционную ветку делает лид с санкции разработчика (раздел
«Приёмка мержа»).

## Приёмка мержа

Лид вливает в интеграционную ветку ветку задачи, сданной ему (`done` с `delivery:
lead`), или ветку без живой сессии по просьбе разработчика. Git-часть ведёт
`accept.py`, гейты лид запускает сам.

1. **План** (`accept.py plan {ветка} --into {интеграционная}`): где мержить, подтянута
   ли ветка к голове интеграционной, какие файлы она меняет. Мерж идёт в дереве, где
   интеграционная ветка открыта, если оно чистое, иначе во временном worktree
   (`accept.py prepare`); в worktree сессий никогда. Дерево, где ветка открыта,
   грязное: СТОП, разработчику.
2. **Санкция.** Превью разработчику: ветка, куда, где, файлы, гейты, сообщение коммита
   `feat({id}): {title}`, статус и комментарий в трекере, push при remote. Одно
   согласие разработчика покрывает всю приёмку и пишется как санкция `A-{n}`
   (`lead.py approve`).
3. **Мерж без коммита** (`accept.py merge`). Конфликт или лишний файл в индексе:
   дерево откатывается само, ничего не коммитится, эскалация разработчику с вариантами
   «директива сессии синхронизироваться и пересдать» и «отложить». Код лид не правит.
4. **Гейты** полным набором на слитом дереве (`verify.*` и критерии адаптера lang);
   e2e сравнивается с базовым набором из `done`. Красный гейт: `accept.py abort`,
   эскалация как в п. 3.
5. **Коммит** (`accept.py commit`), push при remote, запись приёмки `M-{n}` со ссылкой
   на `A-{n}` (`lead.py accept`), статус `done` и комментарий с хешем в трекере.
6. **`advisory` «база сдвинулась»** каждой сессии реестра без `done`, чья база это
   интеграционная ветка: новая голова и изменённые файлы, пересечения с картой файлов
   сессии отмечены. Сессия синхронизируется на ближайшей границе (п. 8 порядка
   действий сессии).
7. Временный worktree снести (`accept.py cleanup`).

## Ветки и worktree вне живых сессий

Лид работает с ветками и worktree только вне работающих сессий, каждое действие по
санкции разработчика `A-{n}`. Санкция может покрывать перечисленный набор действий
(«снести worktree и ветки AL-1151 и AL-1152»).

- Ветка и worktree сессии из реестра, не дошедшей до `done`, принадлежат ей: лид их не
  трогает и отказывает раньше, чем спросит разработчика.
- После `done` и приёмки `M-{n}`, а также для веток без сессии лид может снести worktree
  сессии и удалить её ветку (`accept.py retire`; worktree с submodule по порядку адаптера
  workspace) и создать ветку или worktree под следующую задачу по возможностям порта
  workspace.
- Ветка сессии с `done`, но без приёмки `M-{n}` (невлитая): снос только по явному
  согласию разработчика на снос без мержа, после предупреждения, что это единственная
  копия; `accept.py retire` печатает вершину ветки для восстановления.
- Ветки из `workspace.protected` защищены и от лида. Исключение одно: интеграционная
  ветка, в которую лид вливает по приёмке.

## Пересечения задач

Карты файлов сессий (из `notice` после Research) лид сверяет между активными
сессиями (`lead.py overlaps`). Пересечение: `advisory` обеим сессиям с файлами
и задачей-соседом и одна строка разработчику. В `brief` новой сессии лид передаёт её
пересечения с соседями («швы»), а при приёмке мержа в `advisory` «база сдвинулась»
отмечает файлы, пересекающиеся с картой сессии-получателя.

## Гочи, бэклог и память

Сессия под лидом гочи на Finalize сама не раскладывает: они уходят лиду пунктами
`G{n}` в `notice` (суть, факты с `path:line`, предлагаемый адрес). Лид сводит дубли из
разных задач в одну запись `G-{n}` журнала (`lead.py gotcha`, `gotcha-link`), проверяет
факты и раскладывает (`gotcha-route`):

- дефект или пробел плагина: по `phases.md`, «Finalize: маршрутизация гочей» — сообщение
  сессии `lead.plugin_session`, иначе заметка в `plugin.backlog`, иначе текст разработчику;
  адрес из ответа сессии плагина или путь заметки — в `gotcha-route`;
- особенность проекта: правка CLAUDE.md или проектного адаптера, всегда по санкции
  `A-{n}`;
- личное наблюдение разработчика: память проекта;
- не подтвердилась или дубль известного: `reject` с причиной.

Заметки бэклога и запись памяти лид делает сам или по санкции, как задаёт
`lead.actions` (`backlog`, `memory`; по умолчанию сам, с отчётом в сводке). Заметку
лид пишет из подтверждённой гочи как есть; изменить её смысл или дописать новый текст
в файлы проекта может только разработчик.

**Память.** Сессия лида живёт в основном дереве, поэтому её память и есть память
проекта; сессии в worktree её не видят. Сессии присылают кандидатов в память в `notice`,
лид пишет память своим штатным механизмом и передаёт сессиям относящиеся к задаче
записи в `brief`. Постоянные правила разработчика идут в память, решения по ходу работы
в журнал; повторяющиеся прецеденты лид предлагает поднять в память, CLAUDE.md или
проектный адаптер.

## Регистрация

Сессия регистрируется один раз за сессию, до первого вопроса лиду: `develop` с лидом
в самом начале, до Refine; фазовый скил, запущенный в новой сессии для задачи с лидом,
при запуске. Пока нет состояния задачи (Refine), имя лида берётся из аргумента
запуска. Данные, появившиеся позже (worktree, ветка, база, тир после Start), сессия
сообщает `notice`. Лид заносит сессию в реестр и отвечает `brief`.

- `brief` ждётся тем же будильником. Без `brief` все вопросы задаются локально;
  поздний `brief` принимается, и следующие вопросы идут лиду.
- Решения до `brief` записываются только в `log.md`: пути журнала ещё нет.
- При резюме `register` перечисляет открытые вопросы из состояния. Лид в `brief`
  сообщает их состояние: решённые повторяет `decision`, принятые повторяет `ack`;
  вопрос, которого лид не знает, сессия задаёт заново под тем же номером.

Лид подписывается на уведомление о простое сессии только вместе с настоящим
сообщением ей (`brief`, `ack`, `decision`, `advisory`): отдельная подписка без текста
ненадёжна, а повторная подписка на уже простаивающую сессию срабатывает сразу
и зацикливается. Зависание лид ловит таймером:
уведомление о простое сессии без открытого вопроса и без `done` запускает будильник
лида длиной `lead.stall`; идущий таймер этой сессии не дублируется, любое её сообщение
таймер снимает. Сработавший таймер при сессии, которая всё ещё простаивает без
вопроса, лид сообщает разработчику одной строкой как подозрение на зависание; иначе
закрывает ход молча. На само уведомление о простое лид отвечает одной короткой строкой.

**Перезапуск лида.** Журнал и реестр переживают перезапуск, подписки, таймеры и,
возможно, контекст нет. Лид после перезапуска проверяет, что его сессия снова под своим
именем (до этого сессии его не узнают), перечитывает журнал и шлёт всем сессиям реестра
без `done` `advisory` «лид на связи»; это же сообщение возобновляет подписку на их
простой. Сессия отвечает `register` с открытыми вопросами и недоставленным; так же она
поступает при первой удачной отправке после неудачной.

## Журнал

Журнал лида это файл `_lead/journal.jsonl` каталога артефактов на ветке лида: журнал
событий, который только дописывается. Пишется он только скриптом `lead.py`, никогда
файловыми инструментами: в изолированной worktree-сессии харнесс отклоняет их для
путей вне её дерева. Номера записей выдаёт скрипт под блокировкой файла, поэтому
несколько сессий пишут одновременно без конфликтов. Записи:

- решение `D-{n}`: задача, номер вопроса, пункт, вариант, основание; решение,
  заменённое локальным, помечается ссылкой на него;
- эскалация `E-{n}`: пункт, ожидающий решения разработчика, и её закрытие;
- правило-прецедент: формулировка и задачи, где оно применялось;
- обязательство: триггер и действие («при мерже X сделать Y»);
- санкция `A-{n}`: собственное действие лида и дословное согласие разработчика;
- приёмка `M-{n}`: задача, ветка, куда, коммит, санкция;
- гоча `G-{n}`: суть, задачи-источники, куда разложена;
- реестр сессий: имя, задача, каталог, фаза, карта файлов.

Решения, принятые в сессии локально после `brief`, сессия добавляет в журнал сама
и ссылается на их номера в `notice`; остальное пишет только лид. Путь журнала сессия
получает в `brief`.

Лид повторяет список ожидающих эскалаций в конце каждого ответа разработчику.

## Вето

Разработчик может отменить решение лида `D-{n}`. Лид считает цену отката по состоянию
сессии (`lead.py veto-cost --state {state.yaml сессии}`) и сообщает её до окончательного
решения:

| Класс | Когда | Действие сессии |
|---|---|---|
| 1, `reread` | spec ещё не написан | перечитать решение: ответ в артефакте и строка решения в `log.md` заменяются |
| 2, `restart` | spec или plan готовы, ни один шаг Implement не закоммичен | перезапуск с фазы Spec (механизм `--from`: фазы с Spec убираются из `completed`); незакоммиченная работа шага переделывается |
| 3, `iteration` | шаг Implement закоммичен или Implement завершён | доработка новой итерацией поверх сделанного (механизм возврата задачи: `## Итерация {N}`), не откат |

Вето записывается как эскалация `E-{k}`; новое решение разработчика `D-{m}` с основанием
`developer E-{k}` заменяет `D-{n}` (`lead.py replace`). Затем лид шлёт директиву
с действием класса и основанием `E-{k}`. Вето, меняющее правило, которое служило
прецедентом, лид применяет ко всем решениям по этому правилу: заменяет их новым
решением и шлёт директивы затронутым сессиям, чтобы `precedents` не отдавал устаревшее.

Решение с правом вето лид показывает разработчику один раз, когда принимает его,
и потом в сводке; в каждом ответе список не повторяется. Вето возможно, пока задача
не сдана (`done`); после этого изменение решения это новая задача или итерация.

## Директива и пауза

Директиву (перезапуск с фазы, откат решения) лид шлёт только со ссылкой на решение
разработчика `E-{n}`; директиву без такого основания сессия не исполняет и сообщает
об этом лиду. Сессия исполняет директиву на ближайшей границе: после коммита
текущего шага в Implement, по завершении текущей фазы в остальных. Директива
«синхронизируйся и пересдай» после `done`: сессия открывает Finalize заново
(`finalize` убирается из `completed`, `phase=finalize`), синхронизируется с базой
и шлёт новый `done`. Директивы вето (`reread`, `restart`, `iteration`) сессия исполняет
по таблице раздела «Вето».

Пауза: ручная остановка в сессии задачи единственная жёсткая гарантия. Сообщение
лида до занятой сессии доходит только на следующем вызове инструмента. Просьба
придержать через `advisory` это удобство: сессия останавливается на ближайшей
границе и ждёт `advisory` «продолжить» или слова разработчика. О ручной паузе и её
снятии сессия шлёт `notice`.

## Трекер

Задачу, взятую в работу (есть зарегистрированная сессия или статус `in_work`),
в трекере пишет только её сессия. Лид с санкции разработчика может добавлять к ней
комментарии и передавать сессии правки сообщением; описание такой задачи лид
не меняет. После `done` сессии статус и комментарий о мерже в рамках приёмки пишет
лид по санкции `A-{n}`.

Перед любой своей записью в трекер лид проверяет задачу: взята в работу → только
комментарий; не взята → описание, поля, связи, создание задач. Любая запись лида
в трекер по санкции `A-{n}`; для повторяющегося действия (обновление сводного блока)
разработчик может дать постоянную санкцию, и лид ссылается на её номер.

**Сводный блок.** В режиме назначенной ветки у родительской задачи (`parent`
в `_lead/lead.yaml`) лид ведёт в описании управляемый блок `omixflow:lead` (порт
tracker, «Управляемые блоки»): задачи под лидом, сессия, фаза, ветка, приёмка, открытые
эскалации. Блок строится из журнала (`lead.py board`) и пишется по дисциплине: свежее
описание, замена только блока, запись, перечитать. В режиме мультизадачи сводной
таблицей служит её борд `omixflow:multitask`, его ведут сессии частей.
