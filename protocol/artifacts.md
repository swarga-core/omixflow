# Артефакты задачи

Каталог артефактов задаёт `artifacts.dir` в конфиге, по умолчанию `.tasks`.
Артефакты версионируются в git вместе с кодом (`artifacts.tracked: true`, дефолт):
без этого они не переживают снос worktree и не доезжают до другой машины,
а для мультизадачи это обязательно.

## Раскладка

```
.tasks/
├── {id}/
│   ├── task.md          постановка as-is и финальная, контекст, scope, тир
│   ├── state.yaml       машинное состояние
│   ├── log.md           журнал для человека
│   ├── research.md      Source Files Map, findings, design questions, Handoff (см. ниже)
│   ├── spec.md          дельта: Summary, Changes, Dependencies, Decisions, Out of Scope; в S ещё Research и Steps
│   ├── plan.md          шаги с файлами и тест-чекпоинтами (M, L)
│   ├── review/          findings reviewer'а по проходам: {phase}-pass{N}.json
│   └── reports/         отчёты coder'а и tester'а по заданиям: {phase}-{метка}.md (`runtime.md`, «Отчёт агента»)
├── {id}/                мультизадача
│   ├── multitask.md     определение частей и их постановки, карта зависимостей, волны
│   ├── state.yaml       состояние мультизадачи
│   ├── log.md
│   ├── research.md      синтез частей мультизадачи профиля research
│   └── {part}/          артефакты части: та же структура, что у одиночной задачи
├── _lead/               журнал лида (`lead.md`); только на ветке лида
└── backlog/             хранилище адаптера tracker/local, если он используется
```

Артефакты ревью PR (`.review/`) в git не входят: их добавляет в `.gitignore` скил ревью.

## Коммит артефактов

Скил, который говорит «коммит артефактов» (артефакты фазы, `state.yaml`, `log.md`,
`review/`, `reports/`), действует по `artifacts.tracked`:

- `true` (дефолт): коммит путей каталога задачи `{artifacts.dir}/{id}/` в ветку задачи;
  в мультизадаче с `part_isolation: shared` — правило «Явные пути» (`multitask.md`).
- `false` (трекер хранит артефакты в задаче): ничего не коммитится, след фазы уносит
  публикация в задачу трекера (раздел ниже). Каталог артефактов игнорируется, и `git add -f`
  его путей запрещён: рабочая копия на кодовую ветку не попадает.

Перед любым коммитом сессии (артефакты, шаг, фиксы ревью, слияние) оркестратор сверяет
`git rev-parse --show-toplevel` с корнем проекта или worktree задачи и `git branch
--show-current` с веткой задачи; расхождение — СТОП: каталог сессии ушёл
(`worktree.md`, «Ловушки»), коммит попал бы на чужую ветку.

## Хранение в задаче трекера

Если адаптер tracker объявил возможность `artifacts` (порт tracker, «Артефакты в задаче»),
постоянный дом артефактов — сама задача трекера (карточка доски у адаптера `kanban`).

- **Рабочая копия.** Сессия работает с `{artifacts.dir}/{id}/` в своём дереве, как без
  этой возможности: агенты пишут туда файловыми инструментами, которые в изолированной
  worktree-сессии за пределы её дерева не пишут. Копия временная.
- **На кодовые ветки артефакты не коммитятся** (раздел «Коммит артефактов»): `artifacts.tracked: false`, в `.gitignore`
  кодовых веток `/{artifacts.dir}/*` и `!/{artifacts.dir}/_lead/`: рабочие копии
  игнорируются, журнал лида остаётся на ветке лида (`doctor` проверяет). PR кода несёт
  ссылку на задачу по разделу «Ссылка на задачу» адаптера.
- **Публикация** (`publish`): `state.py` сам публикует после каждого `finish` и после
  `step … done` (шаг Implement: коммит кода, запись в log.md, затем `step done`); на
  Finalize — перед сменой статуса и итогом. Сбой публикации — предупреждение, следующая
  досылает всё. Запись log.md, сделанная после `finish`, уходит со следующей публикацией.
- **Восстановление** (`checkout`): на Start рабочая копия поднимается из задачи трекера,
  куда `create` уже положил `task.md` и минимальный `state.yaml`; на резюме (`develop`),
  если рабочей копии нет, а у задачи в трекере есть состояние пайплайна (новый worktree,
  другая машина, возврат на доработку после `done`).
- **Статус — владение постановкой.** Start переводит задачу в работу без вопроса: пока
  задача не в работе, её постановку можно править через трекер, и публикация затёрла
  бы правку. Эпик сессии не имеет и правится через трекер всегда.
- **Конец рабочей копии.** Finalize со статусом `done` после успешной публикации удаляет
  рабочую копию; при `in_review` она остаётся для доработки.
- **Мультизадача** с таким трекером не поддерживается, если адаптер говорит это в разделе
  «Мультизадача»: refine `--multitask` и start мультизадачи останавливаются.
- **Путь задачи** нигде не хранится и разрешается `path` по id: он меняется со статусом.
- **`task.md`** при создании задачи содержит исходную постановку, Refine дописывает
  уточнённую формулировку (`update_description`), Start доводит до шаблона ниже. После
  Start постановкой владеет рабочая копия: правки идут в неё и уходят публикацией,
  `update_description` трекера отклоняет запись.
- **`state.yaml`** при создании задачи содержит формальную запись: `id`, `kind`
  (`task` или `epic`), `title`, `type`, `owner`, `parent`, `links`, `external`,
  `resolution`, `blocked`, `created`, у перенесённой из другого трекера ещё `imported`
  (откуда); Start дополняет его полями пайплайна, не трогая
  формальные. Статус задачи хранит трекер (у `kanban` — колонка), в `state.yaml` он
  не дублируется.
- **`comments.md`** — комментарии трекера, если адаптер хранит их в задаче; отдельно
  от `log.md`.

## state.yaml

Единственный источник для резюма. Пишется оркестратором при каждом переходе.

```yaml
schema: 1
id: AL-822
kind: task                 # task | multitask | part | epic (эпик: карточка трекера с дочерними задачами)
profile: full              # full | research (protocol/profiles.md); нет ключа = full
mode: pipeline             # pipeline (ведёт develop) | manual (standalone-скилы)
tier: M                    # null у профиля с triage: false
tier_forced: false
phase: implement           # текущая фаза из фаз профиля или done
completed: [refine, start, research, spec, plan]
step: 3                    # текущий шаг плана, только в implement
steps_total: 6
steps_done: [1, 2]
iteration: 1               # номер доработки после возврата; 1 = первая реализация
agents:                    # живые continuation-агенты этой сессии
  coder: coder-AL-822
  reviewer: reviewer-AL-822          # ревьюер артефактов (Spec, Plan)
  reviewer_code: reviewer-AL-822-code  # ревьюер кода (Review), review-cycle.md
session: 3f2a…             # id сессии, в которой созданы agents
syncs:                     # синхронизации с базой (порт workspace, sync; sync.py record)
  - {base_sha: 9f8e7d6, commit: 1a2b3c4, how: merge, at: 2026-10-04T12:00:00Z}
lead:                      # только у задачи, запущенной с лидом (lead.md)
  name: lead-omix          # имя сессии лида
  journal: /abs/…/_lead/journal.jsonl   # путь журнала лида из brief
  asked: 3                 # номер последнего вопроса к лиду (#{n})
  open:                    # вопросы без решения по всем пунктам
    - {n: 3, ack: {Q1: решаю, F3: E-7}}
branch: task/AL-822
base: release/2.3.0
multitask:                 # только для kind: part
  id: AL-9
  part: auth-flow
repos:                     # только для kind: multitask с частями в workspace.repos: снимок
  omix-lib: {ref: auto, sha: 9f8e7d6c5b4a39281706f5e4d3c2b1a098765432}
updated: 2026-09-23T16:00:00Z
```

Управляется скриптом `state.py` (`init`, `get`, `set`, `finish`, `next`; у задачи с лидом `ask`, `ack`, `close`);
скилы не редактируют файл руками.

Правила:

- Резюм читает `phase`, `completed`, `step`, не угадывает по наличию файлов. Если
  файла фазы нет, а `completed` её содержит, это рассинхрон: остановиться и показать.
- `agents` действительны только в сессии `session`: в новой сессии агентов
  предыдущей не существует, `state.py` их очищает при несовпадении, спавн заново.
- Форсированный тир хранится здесь и переживает резюм.
- Часть наследует `profile` из состояния мультизадачи; противоречащий флаг это ошибка.
- Запись снимка `repos` идёт одним JSON-объектом на запись
  (`repos.{name}={"ref":"…","sha":"…"}`), чтобы sha из одних цифр остался строкой.

## research.md

- Секции: Task Summary, Source Files Map, Current State, Existing Patterns, Findings,
  Design Questions; при `HANDOFF` ещё `## Handoff` (`### Facts`, `### Decisions`,
  `### Affected Files and Contracts`, `### Open Questions for Dependents`).
- Кросс-репо: сразу после заголовка `Repository`, `Ref`, `Sha`; пути Source Files Map
  чужого репозитория с префиксом `{repo}:`.
- Design questions типизированы: `Q{n} [blocking]:` с ответом `A{n}:` и
  `Q{n} [deferred]:`. Отложенные вопросы в профиле без Spec могут остаться без ответа.
- Findings исследования нумеруются `R{n}` (и в секции Research объединённого spec.md
  тира S); метка `F{id}` принадлежит findings ревью (`review-cycle.md`), чтобы в log.md,
  spec.md и вопросах лиду их не путать.
- Файл пишется только при `STATUS: done` агента.

## log.md

Журнал для человека. Секция на фазу с заголовком `## {Phase} ✅`, внутри факты:
что создано, сколько findings, сколько проходов, какие решения приняты.
Шаги Implement как `### Шаг {N}: {название} ✅` с файлами, тестами и хешем коммита.
Синхронизация с базой как `### Синхронизация с {base} @ {sha} ✅` со стратегией,
конфликтами («файл — как разрешено») и гейтами на слитом дереве.

Решение в точке решения (`dialog.md`) записывается строкой в секции фазы: в точке
вида `содержание` всегда, в точках видов `маршрут` и `внешнее` только когда выбран
не рекомендованный вариант:

```markdown
- Решение `{id}`: {суть вопроса} → {выбор, условия дословно}. Решил: {основание}
```

Основание по маршруту вопроса (`dialog.md`, `lead.md`): `разработчик` (в этой сессии,
в том числе после таймаута лида); `разработчик, E-{n} через лида: «дословная цитата»`;
`лид, D-{n}, суждение`, `лид, D-{n}, прецедент D-{k}` или `лид, D-{n}, по поручению E-{k}`.
Заметка лида к ответу разработчика (`note` в `decision`) пишется отдельной строкой
со своим основанием `лид, D-{n}`, ответ разработчика остаётся дословным. Ответы на `design-question`, `research-blocking` и `handoff` живут
в артефакте как `A{n}`; в log.md одна строка со ссылкой на них
(`Решение design-question: Q1–Q9 → research.md, A1–A9. Решил: разработчик`).
Доработка после возврата открывает секцию `## Итерация {N}` с замечаниями и повторяет
фазы под ней.

log.md коммитится вместе с артефактом фазы, не позже.

## task.md

```markdown
# {id}: {название}

## Исходная формулировка
{as-is из трекера или от разработчика}

## Контекст
- Трекер: {адаптер}, {ссылки}
- Тип, приоритет: {из трекера}
- Связанные задачи: {links}

## Финальная формулировка
{уточнённая постановка}

## Scope
- Пакеты, модули: {список}

## Tier
- {S|M|L} — {обоснование в одну строку}
```
