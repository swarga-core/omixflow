# Режим worktree

Изоляция задачи в отдельном git worktree. Политика задаётся `workspace.worktree`:

- `off`: работа в основном дереве;
- `optional` (дефолт): включается разработчиком на конкретный запуск;
- `always`: каждая задача и каждая часть мультизадачи получают worktree.

Включение при `optional`:

- **enter-first**: разработчик входит в worktree до запуска скила (`EnterWorktree`
  или фраза «поработай в worktree»). Скилы распознают это и не ветвятся;
- **флаг `--worktree`** у `develop` и `start`: скил сам создаёт worktree вместо ветки
  в текущем дереве.

## Параметры

- Корень: `.claude/worktrees/{id}` для задачи, `.claude/worktrees/{id}-{part}` для части.
- Установка зависимостей: хук `PostToolUse[EnterWorktree]` выполняет
  `workspace.setup` из конфига внутри нового worktree; при непустом
  `workspace.submodules` перед этим инициализирует submodule'ы. Лог:
  `~/.claude/omixflow-wt-setup.log`.
- Артефакты, коммиты и спавн агентов cwd-relative, в worktree изолируются сами.

## Research-worktree

Отдельный вид worktree для кросс-репо ресёрча (`multitask.md`, «Кросс-репо»):

- Корень: `{repo_path}/.claude/worktrees/research-{id}` в чужом репозитории, detached
  на sha снимка. Один на чужой репозиторий в мультизадаче, общий для всех его частей.
- В него не входят: сессия остаётся в домашнем проекте, путь передаётся researcher'у
  как `PROJECT_ROOT`, хук worktree не срабатывает.
- Создание, setup и снос ведёт оркестратор по адаптеру workspace, создание и снос
  с подтверждением.
- Путь детерминирован и в `state.yaml` не пишется (состояние общее для машин, пути
  нет): существование проверяется по месту.
- Накопление предупреждает doctor.

Детект «сессия уже в worktree»:

```bash
[ "$(git rev-parse --git-dir)" != "$(git rev-parse --git-common-dir)" ] && echo in-worktree
```

## Worktree лида

Worktree сессии-лида (`lead.md`, «Ветка лида»):

- Корень `.claude/worktrees/{имя лида}`, ветка `lead/{имя лида}` от базы проекта.
- В него не входят: сессия лида остаётся в основном дереве и обращается к журналу
  и настройкам по абсолютным путям; хук worktree не срабатывает, зависимости не
  ставятся.
- Создание с подтверждением разработчика при старте лида; повторный старт использует
  существующий. Коммиты только каталога `_lead/` с явными путями.

## Базовая ветка

`EnterWorktree({ name })` ветвится от remote default-ветки. Когда base branch проекта
другая (линия `release/*`), worktree создаётся явно и вход идёт по `path`:

```bash
git worktree add .claude/worktrees/{id} -b task/{id} {base}
# затем EnterWorktree({ path: ".claude/worktrees/{id}" })
```

Вход по `path` означает, что `ExitWorktree` этот worktree не удаляет: снос вручную
после интеграции.

## Выход

После PR или интеграции: `ExitWorktree` с `keep` (дефолт, ветка ещё нужна открытому PR)
или `remove`. `remove` блокируется незакоммиченными изменениями: показать список,
не форсить.

## Ловушки

- **Относительные пути у агентов.** Субагент, спавненный из worktree, при относительных
  путях может прочитать основное дерево на чужой ветке и выдать ложные findings.
  Агентам передаются абсолютные пути внутри worktree с явным запретом читать основное
  дерево.
- **Каталог сессии не там, где ждёшь.** Команды без `cd` (`runtime.md`, пролог). Кроме
  `cd`, каталог уносит выход из worktree: он может вернуться в основное дерево, и пустой
  diff выглядит валидным ответом. Особенно опасен каталог чужой ветки внутри дерева —
  worktree доски трекера (`.tasks/board`): `git commit` оттуда уходит на ветку доски.
  Перед любым коммитом — сверка по «Коммиту артефактов» (`artifacts.md`).
- **Основное дерево на чужой ветке.** После `ExitWorktree` перед любой интеграцией
  проверить `git branch --show-current`; если это не ожидаемая ветка, интегрировать
  через временный worktree на нужной ветке, не трогая чужой checkout.
- **Изолированная сессия.** После `EnterWorktree` харнесс отклоняет файловые
  инструменты для путей вне worktree, команды с переменными shell («cannot be shown
  not to be git»), heredoc и `python -c` («too complex to verify»). Пути подставлять
  буквально, артефакты держать внутри worktree, синхронизировать простым `cp`
  с абсолютными путями, циклы разбивать на простые вызовы; вспомогательный скрипт
  класть файлом и запускать одной простой командой. Запись за пределы worktree
  скриптом (журнал лида) проходит.
- **Escape в параметрах инструментов.** `\uXXXX` в параметрах инструментов правки
  и в тексте команд раскодируется в сам символ: в файл, в `grep -F` и в отчёт агента
  попадает литерал, а не escape. Escape пишется скриптом, собирающим обратный слеш
  через `chr(92)`; результат проверяется байтами (`grep -nP '[^\x00-\x7F]'`, `cat -v`).
  Касается агентов, оркестратора и лида.
- **`EnterWorktree` вне репозитория.** Вход в существующий worktree по `path`
  требует, чтобы текущий каталог был внутри git-репозитория: после `cd` в scratchpad
  сначала вернуться в проект.
- **Зависимости.** Симлинки пакетов могут не материализоваться после хука: при первом
  падении гейта с «module not found» повторить `workspace.setup` в самом worktree.
- **Submodule.** Worktree не наследует объекты submodule; без инициализации workspace-пакеты
  из него не резолвятся, и падение гейта выглядит как дефект задачи. Инициализация
  входит в setup хука; для ручного worktree выполнить её самому. Обратная сторона:
  worktree с инициализированным submodule нельзя снести через `git worktree remove`,
  пока существует `{gitdir}/modules` worktree; и нельзя делать `submodule deinit`
  из worktree, он деинициализирует submodule основного дерева через общий конфиг.
  Порядок сноса описан в адаптере workspace.
