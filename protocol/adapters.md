# Порты и адаптеры

Ядро OMIXFlow обращается к внешнему миру только через четыре порта. Порт описывает
контракт, адаптер реализует его. Проект настраивает адаптер значениями в конфиге,
расширяет его правилами или подменяет своим. Ни один скил и ни один агент ядра не
называет инструментов напрямую: только возможности порта.

## Порты

| Порт | Отвечает за | Контракт | Адаптеры в плагине |
|---|---|---|---|
| tracker | задачи: чтение, постановка, статус, комментарии, блок мультизадачи | `adapters/tracker/PORT.md` | youtrack, local, none |
| forge | pull request'ы: создание, чтение, публикация ревью | `adapters/forge/PORT.md` | github, none |
| lang | гейты проверки, конвенции тестов, запрещённые подавления, инструменты навигации | `adapters/lang/PORT.md` | ts |
| workspace | ветки, base branch, worktree, submodule, установка зависимостей, интеграция | `adapters/workspace/PORT.md` | git |

`PORT.md` во фронтматтере перечисляет возможности `required` и `optional`. Адаптер,
не покрывающий `required`, непригоден: `doctor` сообщает об этом до начала работы.

## Файл адаптера

Markdown с фронтматтером. Тело: правила для оркестратора и агентов, сгруппированные по
возможностям. Правила формулируются как инструкции, а не как описание.

```yaml
---
port: tracker                       # какой порт реализует
name: acme                          # имя адаптера, совпадает с именем файла
extends: omixflow:local             # опционально: базовый адаптер, см. ниже
capabilities: [identify, get, update_description, comment, set_status, current_user]
requires:                           # что должно быть в окружении; проверяет doctor
  tools: ["mcp__{server}__*"]       # MCP-инструменты по имени сервера
  bin: [acme-cli]                   # исполняемые файлы в PATH
scripts: {}                         # детерминированные помощники: имя → путь относительно файла
---
```

## Где лежат

Проектная сторона зеркалит дерево плагина и живёт в отдельном каталоге:

```
{project}/.claude/omixflow/
├── flow.yaml                 конфиг
├── tracker/                  адаптеры порта tracker
├── forge/
├── lang/
├── workspace/
├── agents/                   правила проекта к агентам
└── scripts/                  проектные скрипты, затеняют плагинные по имени
```

## Три уровня кастомизации

1. **Конфигурация.** Значения в `flow.yaml`: ключ проекта, шаблон ID, команды гейтов,
   схема веток. Адаптер читает их по ключам, перечисленным в его `PORT.md`.
2. **Расширение.** Файл `.claude/omixflow/{port}/{name}.md` с `extends: omixflow:{name}`.
   Базовые правила действуют, проектные добавляются. Возможности наследуются
   и объединяются.
3. **Замена.** Файл без `extends`. Плагинный адаптер не читается вообще; проектный
   обязан покрыть все `required` возможности порта. Имя может совпадать с плагинным
   (тогда `doctor` предупреждает, что замена полная) или быть новым.

Ссылка `extends` имеет форму `{layer}:{name}`, где layer это `omixflow` (плагин)
или `project` (проектный каталог). Цепочка может быть длиннее одного звена; циклы
запрещены.

## Приоритет правил

При конфликте побеждает более конкретный уровень:

```
flow.yaml  >  проектный адаптер  >  базовый адаптер плагина
```

Расширение может явно отменить базовое правило секцией `## Overrides`: по одному
пункту на правило, с указанием, какое правило базового адаптера заменяется и чем.
Молчаливое противоречие без `## Overrides` считается ошибкой авторинга: `doctor` его
не поймает, поймает ревью адаптера.

## Разрешение в рантайме

Цепочку файлов вычисляет скрипт, а не модель:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve.py" adapter tracker
```

Вывод: пути от базового к листовому. Скил читает их в этом порядке в начале работы
и передаёт агентам, которым они нужны. Агенты не ищут адаптеры сами.

## Агенты

Агенты ядра лежат в `agents/` плагина. Проект может:

- **добавить правила** файлом `.claude/omixflow/agents/{role}.md` с
  `extends: omixflow:{role}`; оркестратор передаёт путь агенту при спавне, потому что
  субагент не получает CLAUDE.md проекта автоматически;
- **заменить агента** двумя способами: проектный агент с тем же именем
  (`.claude/agents/coder.md` перекрывает `omixflow:coder`, так работает сам Claude
  Code) или маппинг в конфиге `agents: { coder: my-coder }` на
  `.claude/agents/my-coder.md`. Скилы получают `subagent_type` из
  `resolve.py agent {role}`, а не пишут имя жёстко.

Замена агента снимает с плагина ответственность за его контракт вывода. Заменяющий
агент обязан выдавать тот же формат, что описан в ядре, иначе оркестратор не сможет
разобрать результат.

## Скрипты

Плагинные скрипты вызываются по имени через `resolve.py script {name}`. Файл с тем же
именем в `.claude/omixflow/scripts/` затеняет плагинный. Так проект подменяет,
например, скрипт гейта, не трогая адаптер.

## Что проверяет doctor

- фронтматтер каждого адаптера в цепочке корректен, `port` совпадает с каталогом;
- `extends` указывает на существующий адаптер, цикла нет;
- объединённые `capabilities` цепочки покрывают `required` порта;
- `requires.bin` есть в PATH, `requires.tools` соответствуют известным MCP-серверам;
- замена без `extends` отмечается предупреждением;
- маппинг агентов указывает на существующие файлы.

## Правила для авторов ядра

- В `skills/`, `agents/`, `protocol/` не упоминаются конкретные инструменты
  адаптеров: ни команд пакетных менеджеров, тест-раннеров и CLI хостинга, ни имён
  MCP-инструментов. Только возможности портов и ключи конфига. Имена адаптеров
  (в таблицах и примерах) допустимы. Правило закреплено тестом `tests/test_lint.py`.
- Ядро не читает `flow.yaml` напрямую ради инструментальных значений: оно спрашивает
  адаптер, адаптер знает ключи.
- Новая возможность порта добавляется сначала в `PORT.md`, затем в адаптеры, затем
  используется ядром. Изменение `required` это breaking change порта, отмечается
  в CHANGELOG.
