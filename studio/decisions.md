# Журнал решений

Решение: что решили, почему, что отвергли. Номера `D-n` сквозные, не переиспользуются;
пересмотр — новая запись со ссылкой на прежнюю.

## D-1. Студия для себя и коллег, не продукт

2026-10-05. Инструмент небольшой команды. Открытый код возможен в будущем, но это
не цель и на решения не влияет.

**Почему:** цель — лучший способ работы, а не рынок; это снимает мультиарендность,
биллинг, общую совместимость.

## D-2. Разработчик — ключевая часть схемы

2026-10-05. Не полная автоматизация, а максимально продвинутый вариант нынешней
работы: пайплайн автоматизирован, разработчик принимает решения и пользуется
удобными инструментами. Агенты работают в клиенте разработчика (Claude Code
и подобные), сервер ведёт пайплайн.

**Отвергнуто:** сервер сам запускает агентов через API, разработчик только смотрит.

## D-3. Пайплайн живёт на сервере, агенты связаны с ним через MCP

2026-10-05. Пайплайн собирается на сервере из отдельных элементов под проект; агент
при старте и на каждом шаге получает инструкции, собранные под него в этот момент.
Состояние, артефакты, статусы и фазы доступны в UI и перенастраиваются.

**Почему:** опыт OMIXFlow — текстовые предписания в каталогах проекта, каскад правил
разрешает сама модель, исполнение неточное и дорогое по контексту.

**Отвергнуто:** пайплайн как markdown-документы в проекте (нынешний OMIXFlow).

2026-10-05. Трекер — не интеграция с внешним, а часть студии, раскрывающая суть
разработки с агентами.
