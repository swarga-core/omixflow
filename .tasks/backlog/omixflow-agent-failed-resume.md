**Контекст.** `runtime.md`, «Ответ без итогов — не отчёт»: ответ без файла по `REPORT_PATH`
оркестратор сразу возвращает агенту сообщением. Статус уведомления `failed` и `FINDINGS_PATH`
reviewer'а там не названы. 0.7.2 (`lead.md`, «Остановленная сессия») описывает остановку
фоновой сессии целиком от сбоя API, а не обрыв одного субагента внутри живой сессии.

**Проблема.** T-7, проход 1 ревью spec: reviewer-T-7 оборвался на ENOTFOUND до записи
`FINDINGS_PATH`; уведомление `failed`, файла нет (log.md T-7, Spec: «оборван ошибкой API до
записи findings»). Оркестратор повторил то же задание тому же агенту по agentId — проход
прошёл. Правила на этот случай нет: другой оркестратор мог заспавнить нового reviewer'а
(контекст и проход потеряны) или счесть проход состоявшимся и спросить лида.

**Предложение.** `runtime.md`, «Ответ без итогов — не отчёт»: уведомление `failed` (сбой API,
сеть) без файла отчёта (`REPORT_PATH`, `FINDINGS_PATH`, `research.md`) — повтор того же
задания тому же агенту SendMessage'ем (по имени, после перезапуска сессии — по id,
`omixflow-agent-resume-by-id`) с теми же путями и строкой «прошлое задание оборвано сбоем,
сверь дерево и продолжи». Это не новый проход ревью и не попытка coder'а в счёт
`limits.*`; решения лида не нужно. Второй `failed` подряд — СТОП и вопрос в точке
`deadlock` (сеть). Ответ агента, который успел записать файл, — обычный отчёт.

**Критерии приёмки.** Правило в runtime.md, ссылки из review-cycle.md и implement 2.2; обрыв
субагента от сбоя API не теряет проход и не требует решения лида.
