**Контекст.** `protocol/review-cycle.md`, шаг 3: исполнитель — по категории (`code` и
`spec-sync` — coder, `tests` — tester). Категория в `agents/reviewer.md` («Categories») —
природа дефекта (качество кода, покрытие), не место правки.

**Проблема.** T-2, ревью кода, проход 1: #1, #2 `[tests]` — `packages/server/src/db/migrate.test.ts`,
#3 `[tests]` — `seed.test.ts`, #4 `suggestion [code]` — тот же `migrate.test.ts:2` (импорт `pg`
по умолчанию вместо именованного). По букве шага 3 #4 ушла бы coder'у, и на один файл
в проходе пришлись бы два агента. Оркестратор отдал всё tester'у («все правки в тестовых
файлах; #4 категории code — импорт в тестовом файле, исходники не трогаются», log.md T-2) —
решение верное, но импровизация вопреки протоколу.

Обратный случай протокол тоже не покрывает: `tests` с правкой исходника (шов для теста) —
tester исходники не меняет.

**Предложение.** Шаг 3 — маршрут по файлам правки, категория — по умолчанию:
- фикс только в тестовых файлах (шаблоны имён из `test_conventions` адаптера lang) — tester,
  любой категории;
- фикс в исходниках — coder, и для `tests` (шов, тестовый хелпер в исходниках); тесты к нему —
  tester'у следом, по существующему порядку «по зависимости»;
- один файл в проходе — один агент; спорное — строкой в log.md.
Категорию reviewer ставит по природе дефекта, как сейчас: подмена категорией места исказила бы
статистику и решения по `architecture`.

**Критерии приёмки.** Шаг 3 `review-cycle.md` называет маршрут по файлам; находка `code` только
в тестовом файле уходит tester'у без импровизации; в проходе на один файл назначен один агент.
