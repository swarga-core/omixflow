# OMIXFlow: дополнительные read-only репозитории у части (`reads`)

- **Репозиторий:** omixflow (`scripts/multitask.py`, `skills/start`, `skills/research`,
  `agents/researcher.md`, `protocol/multitask.md`, `protocol/artifacts.md`,
  `protocol/runtime.md`, тесты)
- **Происхождение:** AL-1147 (профили пайплайна), первая попытка запустить
  research-мультизадачу аудита паритета legacy → eps-eal-omix. Замечание агента-планировщика:
  часть читает ровно один репозиторий, а аудит паритета по определению двухрепозиторный.
- **Тип:** Feature
- **Тир:** M (плагин)

## Проблема

После AL-1147 часть research-мультизадачи привязана к одному репозиторию: колонка `repo`
блока, один `PROJECT_ROOT` у researcher'а, `REPO` только для чужого репозитория, группировка
планировщика «активен один репозиторий за раз». Правило повторено в `refine` (шаг 1,
«в немутирующем профиле часть читает ровно один репозиторий»), в `multitask.md`
(«Планировщик», «Кросс-репо») и в шаблоне спавна researcher'а в `runtime.md`.

Аудит паритета (16 областей, каждая сверяет старое поведение в `eal-legacy` с новым в
eps-eal-omix) в эту модель не укладывается. Обход без правок плагина, двухэтапная
декомпозиция (`legacy-{area}` в чужом репозитории строит инвентарь поведения с `path:line`
в Handoff, `parity-{area}` в домашнем зависит от неё и получает инвентарь через `INPUTS`),
формально работает по протоколу, но:

- 32 части вместо 16; при `multitask.parallel_parts: 4` и последовательных репозиториях
  прогон вдвое длиннее, плюс 16 диалогов завершения частей с Handoff;
- сравнивающий researcher не видит старый код, а видит только то, что инвентаризатор счёл
  нужным записать; инвентаризатор не знает, что окажется важным на стороне нового кода,
  обратной связи нет. Ценность аудита именно в том, что один агент держит оба кода перед
  глазами и может проверить крайний случай, которого нет в инвентаре.

Техническая причина правила «один репозиторий» не в протоколе, а в навигации: LSP-инструменты
держат один активный проект на сессию. Второй корень у researcher'а не получит символьной
навигации, только чтение файлов и текстовый поиск. Для аудита паритета этого достаточно:
навигация нужна по новому коду, старый читается как текст.

## Предлагаемое решение

Дополнительные read-only репозитории у части. Основной репозиторий части (`repo`) остаётся
единицей группировки планировщика и активации навигации; `reads` добавляет корни только для
чтения. Большая часть механики уже есть после AL-1147: `workspace.repos`, снимок sha в
state мультизадачи, research-worktree, проверки doctor.

### Блок мультизадачи (`scripts/multitask.py`, `protocol/multitask.md`)

- Опциональная колонка `reads` после `repo`: имена из `workspace.repos` через запятую,
  `—` или отсутствие = ничего. `Row.reads: List[str]`; `render` печатает колонку только
  когда хоть одна строка её использует (legacy-блоки байт-в-байт как раньше).
- `validate(rows, profile, repos)`: каждое имя из `reads` есть в `--repos`; имя не
  совпадает с `repo` той же строки; `reads` допустим только в немутирующем профиле
  (как `repo`). Зарезервированное имя `home` обозначает домашний корень: так часть
  с чужим `repo` может читать домашний репозиторий; у части с `repo: —` значение `home`
  в `reads` отклоняется как дубль.
- `set reads=` только у `pending` (как `repo`); `seed --reads` с одним значением на часть
  в порядке `--parts` (как `--repo`).
- `block_meta().repos` возвращает объединение имён из `repo` и `reads` (без `home`):
  Start снимает sha для всех.

### Start (`skills/start`)

Без изменений в логике: снимок делается для `meta.repos`, который теперь включает `reads`.
Репозиторий, впервые встреченный в `reads` части, снимается при старте этой части (то же
правило, что для `repo`).

### Планировщик и спавн (`skills/research`, `protocol/runtime.md`)

- Группировка и правило «один корень на активный репозиторий» без изменений: ключ
  группировки только `repo`.
- Перед запуском части сверка HEAD со снимком выполняется для `repo` и для каждого из
  `reads`; research-worktree создаётся по тому же правилу и разделяется всеми частями,
  которые читают этот репозиторий, в любой роли (D21 из spec AL-1147 уже требует один корень
  на репозиторий).
- Новый параметр спавна `REPOS:` (список `{name}: {root} ref={ref} sha={sha}`, для `home`
  корень домашнего проекта). Передаётся только при непустом `reads`.

### Researcher (`agents/researcher.md`)

- Входы: `REPOS` (read-only корни). Правило инструментов: навигация активируется только на
  `PROJECT_ROOT`; корни из `REPOS` читаются как файлы и текстовым поиском, попытка
  активировать в них проект запрещена.
- Шапка research.md: после `Repository/Ref/Sha` строки `Reads: {name} ref={ref} sha={sha}`
  на каждый корень. Пути Source Files Map из `REPOS` с префиксом `{name}:`, как у чужого
  `repo` (правило префиксов уже в `artifacts.md`).
- Handoff без изменений.

### Протокол и документация

- `multitask.md`: колонка `reads` в списке колонок и во втором примере блока; в «Кросс-репо»
  абзац про снимок и worktree для `reads`; в «Планировщик» одна фраза про `REPOS`.
- `refine`: шаг 1a спрашивает и `reads` (multiSelect по `resolve.py repo --list` плюс
  `home`); формулировка «часть читает ровно один репозиторий» → «часть навигирует по одному
  репозиторию и может читать другие».
- `artifacts.md`: строки `Reads:` в описании шапки research.md. `runtime.md`: `REPOS` в
  таблице параметров researcher'а. `glossary.md`: термин «репозиторий чтения».
- CHANGELOG с пометкой **protocol** (multitask, artifacts, runtime, glossary). Порты не
  меняются: колонки блока не входят в контракт tracker PORT, `workspace.repos` уже есть.

### Тесты

- `tests/test_state_multitask.py`: парсинг и рендер `reads` (колонка только при
  использовании, legacy round-trip), `validate` (неизвестное имя, имя = `repo`, `reads`
  в `full`), `set reads=` только у pending, `seed --reads`, `meta.repos` как объединение,
  хирургический `set` сохраняет колонку.
- Линт «инструменты не в ядре» остаётся зелёным (формулировка про навигацию без имён).

## Обходной путь до реализации

Двухэтапная декомпозиция описана выше. Блоки совместимы: колонка `reads` опциональна,
при появлении расширения parity-части можно завести новой волной с `repo: —`,
`reads: eal-legacy`, не трогая уже завершённые части.

## Критерии приёмки

- `python3 -m unittest discover tests` и `claude plugin validate .` зелёные; блоки и
  state без `reads` работают без изменений (байт-в-байт round-trip).
- Живой прогон: research-мультизадача из eps-eal-omix с частью `repo: —`,
  `reads: eal-legacy`: снимок `eal-legacy` в state мультизадачи, researcher получает `REPOS`,
  Source Files Map содержит пути с префиксом `eal-legacy:`, шапка research.md содержит
  `Reads:`, HEAD-сверка перед запуском выполнена для обоих корней.
- Часть с `reads`, чей репозиторий чтения ушёл от снимка, работает из research-worktree,
  общего с частями, у которых этот репозиторий основной.

## Ограничения

- Навигация (LSP) только по основному репозиторию части; `reads` это файлы и текстовый
  поиск. Ограничение фиксируется в контракте researcher'а, не обходится.
- Мутирующие профили `reads` не поддерживают (как и `repo`).
- Ограничение «один активный репозиторий за раз» для группировки не меняется.
