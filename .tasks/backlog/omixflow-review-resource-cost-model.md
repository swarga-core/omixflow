**Контекст.** Finding reviewer'а — `problem` и `recommendation` (`agents/reviewer.md`,
контракт JSON); аспект ревью кода «security (injection vectors, boundary validation)».
О ресурсных лимитах (сколько работы сервер делает на один вход) правил нет. Лимит проходов —
`limits.review_passes` (3), сверх него — проход с разрешения разработчика
(`review-cycle.md`, «Лимит проходов»).

**Проблема.** T-6, F7 (`suggestion [architecture]`, предсуществующее): валидация graphql-js
квадратична на повторах поля и идёт до `checkCost`. Три фикса подряд закрывали конкретную
пробу ревьюера, следующий проход находил новый вариант той же стоимости:
1. Проход 3: `{ me { id ×4800 } }` — 609 мс. Фикс — лимит числа узлов полей (≈1000).
   Решение D-112: 4-й проход сверх лимита.
2. Проход 4: под лимитом — повторы одного ключа ответа с аргументами и подвыборкой:
   `{ project(key: "x") { id } }` ×498 (996 полей, 12,5 КБ) — 2240 мс, с псевдонимом ×450 —
   1771 мс, через 249 фрагментов — 562 мс. Фикс — лимит повторов ключа (10) и бюджет работы.
   Решение D-116: 5-й проход, «обход через фрагменты — лимит на фрагменты в том же проходе».
3. Проход 5, первый вердикт: развороты фрагментов — `{ me { ...F0 … ...F170 } ×10 }`
   (4991 токен) — 90 мс, квадратично по числу разворотов. Фикс — `maxFragmentSpreads: 30`
   в том же проходе, затем approve.
Модель стоимости появилась в находке только на проходе 5: OverlappingFieldsCanBeMerged
перебирает пары полей с одним ключом ответа и пары разворотов в наборе и между наборами.
До неё recommendation называла пробу, и architect со coder'ом закрывали пробу. Итог —
2 прохода сверх лимита и два вопроса разработчику (E-17, E-18).

**Предложение.**
- `agents/reviewer.md`, аспекты ревью кода: неограниченная работа на входе (время, память,
  размер ответа) — отдельный пункт рядом с security. Такой finding называет модель стоимости:
  какой параметр входа даёт рост и какой (`O(k²)` по числу полей с одним ключом в слитом
  наборе), и семейство обходов (псевдонимы, фрагменты, вложенность, слияние наборов).
  Recommendation ограничивает параметр модели, а не пробу.
- Фикс по такому finding (spec — architect, код — coder): приёмка — пробы ревьюера и
  варианты семейства; отчёт coder'а — пробы с временами до и после.
- Категория остаётся по природе дефекта (`code` или `architecture`); новая категория не
  нужна.

**Критерии приёмки.** Аспект и требование к модели стоимости в `reviewer.md`; фикс в
`review-cycle.md`, шаг 3, или в coder.md с приёмкой по семейству; на следующей находке
такого рода фикс закрывается за один проход.
