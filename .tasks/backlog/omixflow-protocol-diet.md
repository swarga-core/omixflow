# OMIXFlow: диета протокола — что сессия читает до первого действия

- **Репозиторий:** omixflow (`skills/*`, `protocol/*`, `agents/*`)
- **Происхождение:** повторный прогон лида 2026-10-04 (10b, песочница `omixflow-sandbox`):
  сессия задачи тира S прочла около 100K токенов протокола до регистрации у лида,
  контекст сессии дошёл до 272K к концу задачи, контекст лида до 148K к `done` одной
  задачи (кэш-чтение сессии 24,3M токенов).
- **Тип:** Feature (стоимость)
- **Тир:** M

## Проблема

Скилы ссылаются на протокол списком файлов в прологе («Пролог: runtime.md… Фазы…
Тиры… Мультизадача… Профили… Диалог…»), и оркестратор читает их целиком до первого
действия, независимо от того, понадобятся ли правила этой задаче. Задача тира S без
мультизадачи и без кросс-репо платит за `multitask.md`, `profiles.md`, `worktree.md`
и полный `lead.md`. Каждый следующий ход перечитывает этот контекст из кэша: цена
растёт с длиной сессии, а с лидом ещё и с числом сессий.

## Предлагаемое решение

1. Замерить по транскриптам прогонов, какие файлы и сколько токенов читает каждая фаза
   и роль (оркестратор, лид, агенты).
2. Для каждого скила задать обязательный минимум до первого действия и правила
   «читать по требованию» с условием (например, `multitask.md` только при блоке
   мультизадачи, `worktree.md` только при `--worktree`, раздел `lead.md` для сессии
   без лида не нужен вовсе).
3. Разделить крупные документы протокола на ядро и справочник там, где правило нужно
   редко; сессии задачи под лидом нужен раздел «Порядок действий сессии», а не весь
   `lead.md`.
4. Линт: пролог скила перечисляет только обязательный минимум; ссылки «по требованию»
   несут условие.

## Критерии приёмки

- Повторный прогон задачи тира S в песочнице: контекст сессии до первой фазы не больше
  половины нынешнего, к концу задачи заметно меньше 272K.
- Поведение пайплайна не меняется: тесты и живой прогон проходят те же сценарии.

## Ограничения

- Правило по-прежнему живёт в одном месте; диета меняет, когда его читают, а не где
  оно записано.
