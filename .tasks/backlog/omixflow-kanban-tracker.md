# OMIXFlow: трекер kanban — доска на отдельной ветке, карточка как досье задачи

- **Репозиторий:** omixflow (новый адаптер `adapters/tracker/kanban.md` и скрипт
  `adapters/tracker/kanban/board.py`, порт tracker, `protocol/artifacts.md`,
  `scripts/state.py`, `doctor`, фазовые скилы, скил `lead`)
- **Происхождение:** обсуждение с разработчиком 2026-10-04 после выпуска 0.3.0;
  решения ниже согласованы.
- **Тип:** Feature
- **Тир:** L; ведётся по плану работ, без задач в трекере, шаг за шагом с отчётом
  и вопросами разработчику
- **Статус:** реализовано в 0.4.0 (2026-10-05); первый реальный проект — mewria
  (переезд с `local` 2026-10-05). Отложенное — раздел «Ограничения».

## Проблема

Трекер `local` хранит задачи файлами на кодовых ветках. Живые прогоны лида показали
цену: запись зависит от того, где стоит сессия (Refine до Start пишет в защищённую базу),
статус размазан по веткам до мержа, переименования и сгенерированный индекс конфликтуют,
записи лида сдвигают интеграционную ветку. Артефакты задачи (`.tasks/{id}/`) тоже живут
на ветке задачи: лид не видит их без мержа, они засоряют PR и двигают базу.

## Решения

1. **Доска на отдельной ветке.** Ветка `board` (`tracker.branch`) без общей истории
   с кодом; в каждом клоне открыта worktree в `.tasks/board/` (`tracker.dir`), кодовые
   ветки этот путь игнорируют. Одна правда для всех сессий и разработчиков, история
   в `git log` доски, обмен через push.
2. **Колонки — папки:** `backlog/`, `working/`, `review/`, `done/`. Статус задачи это
   папка её карточки и больше нигде не дублируется. Статусы порта: новая задача →
   `backlog`, `in_work` → `working`, `in_review` → `review`, `done` → `done`; отмена —
   `done` с `resolution: canceled`; блокировка — поле `blocked` в своей колонке.
3. **Вид доски** — сгенерированный `board.md`; `README.md` доски остаётся точкой входа
   и не генерируется.
4. **Карточка — папка** `{колонка}/{ID}-{slug}/`, досье задачи:
   - `task.md` — постановка: при создании исходная, Refine дописывает уточнённую, Start
     доводит до шаблона артефакта (контекст, финальная формулировка, scope, тир);
   - `state.yaml` — формальная запись задачи (id, вид, название, тип, владелец,
     родитель, связи, внешний id, резолюция, блокировка, даты) и, с Start, состояние
     пайплайна; создаётся минимальным при создании карточки, Start его дополняет;
   - артефакты пайплайна: `log.md`, `research.md`, `spec.md`, `plan.md`, `review/`;
   - `comments.md` — комментарии трекера (дописываются в конец), отдельно от `log.md`.
5. **Идентификаторы** `{prefix}-{n}`, префикс из `tracker.project`. Номер выдаётся как
   максимальный + 1 после `fetch` и возвращается только после успешного push: при отказе
   push номер вычисляется заново, на неопубликованный номер сослаться некому.
6. **Все операции — скрипт `board.py`.** Запись: блокировка в общем `.git` → `fetch` и
   rebase ветки доски → изменение → коммит → push, при отказе повтор. `get` отдаёт
   ревизию, `describe` её проверяет: чужая запись между чтением и записью отклоняет
   запись. Чтение из локальной worktree без сети; `board.py pull` на старте `develop`
   и лида. Без remote при включённом push запись падает с понятной ошибкой.
7. **Несколько разработчиков сразу:** `tracker.push`, rebase и повторы, конфликт только
   при одновременной правке одной карточки.
8. **Артефакты: рабочая копия и публикация.** Изолированная worktree-сессия не может
   писать файловыми инструментами вне своего дерева, а агенты пишут артефакты именно
   ими. Поэтому сессия работает с `.tasks/{id}/` в своём дереве, как сейчас, а
   `board.py publish` копирует артефакты в карточку и коммитит доску (после каждого
   `state.py finish`, после коммита шага, на Finalize); `board.py checkout`
   восстанавливает рабочую копию из карточки для резюма в новой сессии или на другой
   машине. Доска единственное постоянное хранилище; на кодовые ветки артефакты не
   коммитятся (`.tasks/` игнорируется), PR кода несёт ссылку на карточку.
9. **Путь карточки по id.** Путь меняется при переезде между колонками, поэтому нигде
   не хранится и разрешается `board.py path {ID}`. Переезды только на границах фаз:
   Start (`backlog` → `working`) и Finalize (→ `review` или `done`).
10. **Возможность порта `artifacts`** (необязательная): адаптер хранит артефакты задачи
    в карточке; ядро публикует и восстанавливает их, только если адаптер её объявил.
    `youtrack` и `local` работают как раньше.
11. **Эпики.** Эпик — карточка `kind: epic`, у дочерних задач поле `parent`. По колонкам
    эпик двигается вручную; `board.md` показывает прогресс дочерних, а когда все они
    в `done`, лид или скил предлагает закрыть эпик. Термин «эпик» разрешён словарём:
    это родительская карточка с дочерними задачами, а не мультизадача.
12. **Мультизадача** в первой версии kanban не поддерживается: блок мультизадачи
    в карточке → СТОП с объяснением.
13. **`local` остаётся** как есть; перенос с него: `board.py import --from-local`.

## Живой прогон 2026-10-05

**10a, скриптом** (настоящие `board.py`, `state.py`, `doctor.py` в том порядке, в каком
их вызывают скилы; 15 с): переезд `local` → kanban с уборкой кодовой ветки; подхват
доски вторым разработчиком по подсказке `doctor`; эпик и две дочерние задачи; две
параллельные сессии в worktree разных клонов (около 30 записей доски с push у каждой,
без потерь и конфликтов); резюм после потери worktree из карточки (шаг 1 и его запись
в log.md на месте); squash в `main`, `done`, удаление рабочих копий, закрытие эпика.
Находка: трейсбек `board.py` на несуществующем `--from` (исправлено). Повтор — 0 находок.

**10b, живая сессия** (`refine TK-5` эпика, `develop TK-6 --tier=S`, около 30 минут):
подтверждены режим эпика в refine (состав, создание с `parent`), `pull` в начале
`develop`, Start без вопроса о статусе с переездом эпика в `working`, публикации после
фаз и шагов, гоча в карточку доски, комментарий, `done`, вопрос о закрытии эпика,
удаление рабочей копии. Находки: дочерние задачи эпика без уточнённой секции
(Start предложил бы refine) и ложный `complete` при частичной декомпозиции —
исправлено в refine и адаптере; вне kanban — нет lang-адаптера Python, невидимые
символы в тестах tester'а, `cfg.py get` (черновик `issues-tk-6.md`).

Наблюдение: около 13 коммитов доски на задачу (публикация на фазу и шаг); история
доски шумная, но рабочая.
