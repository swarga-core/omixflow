**Контекст.** Каждый проход ревью получает `FINDINGS_PATH:
{TASK_DIR}/review/{phase}-pass{N}.json` (`review-cycle.md`, шаг 1). Протокол знает только
проходы; перепроверки внутри прохода в нём нет. От `FINDINGS_PATH` зависят и имена фоновых
гейтов reviewer'а (`{label}-{gate}`, метка — имя файла без `.json`, 0.6.1).

**Проблема.** T-6, проход 5 (дополнительный, решение D-116 с оговоркой «обход через
фрагменты — лимит на фрагменты в том же проходе»): reviewer-T-6-code-2 дал
`request_changes`, blocking [7]. Оркестратор по оговорке провёл фикс в том же проходе и
отдал перепроверку тому же reviewer'у с тем же `FINDINGS_PATH`. Итоговый `approve` записан
поверх: в `review/review-pass5.json` — `findings: 0`, `resolved: 1`, `approve`, первый
вердикт с пробами остался только в log.md. Тот же путь — та же метка гейтов: фоновый гейт
перепроверки заменил бы лог гейта первого вердикта (`gate.py` снимает идущий прогон
с тем же именем).

**Предложение.**
- Каждый вызов reviewer'а пишет свой файл: перепроверка внутри прохода (только по решению
  разработчика) — `FINDINGS_PATH: {TASK_DIR}/review/{phase}-pass{N}-recheck{K}.json`.
  Оркестратор не отдаёт reviewer'у путь, по которому уже есть файл.
- `review-cycle.md`: перепроверка внутри прохода — явный случай со своим файлом и строкой
  в log.md; она не открывает новый проход и не тратит лимит.
- Массив вердиктов в одном файле (вариант лида) отвергнут: reviewer переписывал бы JSON
  чтением-записью, а скилы читают контракт как один объект.
- Линт или проверка в скиле: имена `FINDINGS_PATH` уникальны на задание, как метки
  `REPORT_PATH`.

**Критерии приёмки.** По файлам `review/` видна вся история вердиктов прохода; у
перепроверки своя метка гейтов.
