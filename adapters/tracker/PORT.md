# Порт tracker

Источник задач: откуда пайплайн берёт постановку, куда пишет уточнения, статусы,
комментарии и блок мультизадачи. Ядро оперирует абстрактными статусами
и абстрактными операциями; адаптер отображает их на конкретный трекер.

## Возможности

| Возможность | Обязательна | Что делает | Кто использует |
|---|---|---|---|
| identify | да | по строке аргумента определить, это id задачи этого адаптера или свободная формулировка; вернуть нормализованный id | все скилы на входе |
| get | да | вернуть задачу: id, summary, description, type, priority, произвольные поля, ссылки | refine, start, develop |
| update_description | да | заменить описание целиком; ядро использует это для управляемых блоков и уточнённой формулировки | refine, multitask |
| comment | да | добавить комментарий | start, finalize, multitask |
| set_status | да | перевести задачу в абстрактный статус: `in_work`, `in_review`, `done`; отображение в `tracker.status_map` | start, finalize |
| current_user | да | логин текущего пользователя для `owner` и подписи | multitask, review |
| comments | нет | прочитать комментарии, с пагинацией если нужно | refine, develop при возврате на доработку |
| create | нет | создать задачу из постановки с дефолтами `tracker.create_defaults` | create |
| link | нет | связать задачи | create, парные задачи |
| search | нет | найти задачи по запросу адаптера | refine, yt-commit-подобные сценарии |
| tag | нет | добавить или снять тег | multitask (`multitask`) |
| parts_as_issues | нет | материализовать части мультизадачи дочерними задачами; зарезервировано | multitask, будущее |
| artifacts | нет | хранить артефакты задачи в самой задаче трекера: `path`, `publish`, `checkout` (раздел «Артефакты в задаче») | start, implement, finalize, develop, lead |
| batch | нет | выполнить несколько записей (create, link, comment, set_status, update_description, публикация `artifacts`) одной транзакцией: все или ни одной (раздел «Пакетная запись»); без возможности скилы вызывают операции по одной | refine (эпик), finalize |

## Управляемые блоки

Ядро хранит в описании задачи блоки между маркерами
`<!-- omixflow:{kind}:start[ key=value…] -->` и `<!-- omixflow:{kind}:end -->`.
Маркер начала может нести атрибуты (грамматика в `protocol/multitask.md`,
«Идентификация»). Каждый маркер занимает строку целиком; маркер, процитированный
внутри фразы, маркером не является. Адаптер обязан уметь: найти блок по началу строки
маркера начала независимо от атрибутов, заменить содержимое только между маркерами,
сохранив строку маркера начала вместе с атрибутами как есть, дописать блок в хвост,
если его нет. Правило «прочитать перед записью, перечитать после» описано
в `protocol/multitask.md` и обязательно для любой реализации `update_description`.

## Артефакты в задаче

Адаптер с возможностью `artifacts` хранит артефакты задачи (`task.md`, `state.yaml`,
`log.md`, `research.md`, `spec.md`, `plan.md`, `review/`, `reports/`) в самой задаче трекера, а не на
кодовой ветке. Три операции:

| Операция | Что делает |
|---|---|
| `path {id}` | абсолютный путь хранилища задачи; путь может меняться со статусом, поэтому нигде не хранится и всякий раз разрешается заново |
| `publish {id} {TASK_DIR}` | скопировать артефакты из рабочей копии в хранилище задачи и зафиксировать (для доски на ветке: коммит и push) |
| `checkout {id} {TASK_DIR}` | восстановить рабочую копию из хранилища задачи |

Адаптер объявляет их скриптом `scripts.artifacts` (`resolve.py adapter-script tracker
artifacts`), принимающим `path {id}`, `publish {id} --from {TASK_DIR}` и
`checkout {id} --to {TASK_DIR} [--force]`; через него `state.py` публикует сам.

Когда ядро их вызывает и как рабочая копия соотносится с хранилищем, описывает
`protocol/artifacts.md`, раздел «Хранение в задаче трекера». Без этой возможности
артефакты живут на ветке задачи, как раньше.

## Пакетная запись

Адаптер с возможностью `batch` принимает список записей и выполняет их одной транзакцией:
у трекера на ветке git это один коммит и один push. Отказ любой записи или публикации
отменяет весь пакет, трекер остаётся как был. Задача, созданная в пакете, получает
временное имя, на которое ссылаются следующие записи того же пакета (связь, родитель).
Скил, которому нужно несколько записей подряд, при возможности `batch` собирает их
в один пакет; формат пакета — в адаптере.

## Уточнённая формулировка

Refine дописывает в описание секцию `## Уточнённая формулировка`, не удаляя исходный
текст. Start читает эту секцию, если она есть.

## Разделы адаптера по ситуации

Ядро читает эти разделы файла адаптера, если они есть:

| Раздел | Что описывает | Кто читает |
|---|---|---|
| «Свежесть» | как обновить локальную копию трекера перед чтением | develop и lead в начале работы |
| «Ссылка на задачу» | как сослаться на задачу из PR; без раздела — id задачи | finalize |
| «Мультизадача» | что мультизадача адаптером не поддерживается | refine `--multitask` и start мультизадачи: СТОП |
| «Эпики» | эпик, родитель дочерних задач: как узнать эпик, создать дочернюю задачу, проверить, что все дочерние закрыты, закрыть эпик | refine эпика; finalize и лид после перевода дочерней задачи в `done` |

## Конфиг

```yaml
tracker:
  adapter: youtrack           # имя адаптера
  project: AL                 # ключ проекта, если трекер требует
  id_pattern: "^[A-Z]+-\\d+$" # переопределение шаблона id адаптера
  status_map:                 # абстрактный статус → статус трекера
    in_work: In Work
    in_review: Waiting for review
    done: Finished
  create_defaults:            # поля при create
    Type: Task
  dir: .tasks/backlog         # для адаптера local: каталог задач; для kanban: где открыта доска
  branch: board               # для kanban: ветка доски
  push: true                  # для kanban: пушить ветку доски после каждой записи
```

## Авторинг адаптера

- Каждая возможность описывается как инструкция: какой инструмент вызвать, с какими
  аргументами, что вернуть, какие ограничения инструмента учесть.
- Ограничения трекера (лимиты пагинации, отсутствие патча описания, права на теги)
  документируются в адаптере, а не в ядре.
- Адаптер `none` реализует `required` пустыми операциями и хранит статус только
  в `state.yaml`; он нужен, чтобы пайплайн работал без трекера.
