MEW-28 (G-5, mewria-client-lead) и MEW-34 (G-72, mewria-sim-lead). Попутно найдена и исправлена
ошибка 0.9.4 в счёте синхронизации. Фаз, агентов и проходов не прибавилось.

## 2. Что было и что меняется

**G-97, план посреди Implement.** `plan.py check` рассчитан на план до Implement: CREATE файла,
который уже есть, — «already exists (MODIFY?)». В T-16 оркестратор сверял план с деревом после шагов
1–3 и после шага 7 и получил 9 и 17 строк, почти все — о файлах, которые создали сами сделанные шаги;
среди них не видно расхождения у шага, который ещё впереди. Теперь `check` читает `steps_done` из
`state.yaml`: пути сделанных шагов с деревом не сверяются, поля и чекпоинты проверяются как прежде.
Следующие шаги видят дерево, а не Files сделанных: если сделанный шаг создал файл не там, MODIFY
впереди скажет «not in the tree» — то самое расхождение, которое шум прятал. Вывод — строка «(steps
1, 2 are done: their paths were not checked against the tree)» по шагам текущей итерации плана, в
JSON — `done_steps` в порядке плана.

**G-5, грязный файл вне слияния.** В mewria правило проекта R-2 разрешает синхронизацию при правках
фаундера в `knowledge/`, если база их не трогает. В MEW-28 `report.py check --conflicts none` без
`--baseline` взял в дельту всё незакоммиченное, в том числе `knowledge/lore/purr-world.md` с
кириллицей, и вернул отчёт за BYTES CHECK. Теперь скил implement («1a») снимает `report.py baseline`
перед заданием coder'у, когда слияние уже остановилось, и сверяет отчёт с ним: в дельте всё, что
coder изменил, в том числе вне слияния, а чужая правка в грязном дереве — нет: файл, которого слияние
не касается, считается против своего blob'а в baseline, и на coder'а идут только его строки (второй
круг ревью: первая версия считала такой файл трёхсторонне, и строка coder'а в грязном файле приносила
ему все строки разработчика). Без baseline (старая
сессия, ручной вызов) из дельты выходят файлы, которые есть в HEAD, не меняются ни одной стороной с
общей базы (`diff {base} HEAD`, `diff {base} {другая сторона}`) и не конфликтные, — с предупреждением
«вне слияния (… не сверены): …». Новый файл (его нет в HEAD — шов-тест coder'а) остаётся в дельте.
`--conflicts none` — конфликтов нет, вердикт пишет «конфликтов нет»; если `MERGE_MSG` называет
конфликты, сверяются они, а расхождение — факт; `none` вместе с файлами и пустое значение (пустая
подстановка `{CONFLICTS}`) — ошибка вызова.

На реплее синхронизации T-16 (ниже) с кириллической строкой в `README.md`, которого не меняет ни одна
сторона: 0.9.5 возвращает отчёт с «BYTES CHECK не называет файлы … ['README.md']», 0.9.6 даёт
предупреждение «вне слияния: README.md».

**G-72, единица счёта MUTATIONS.** `report.py` считает новым тестом каждую строку, которую находит
`tests.declaration` адаптера lang; у mewria это каждый `[TestCase(…)]`. Правило coder'а говорило
«строка на каждый новый тест», а ошибка называла только число по файлу — в MEW-34 coder дал строку
на метод (22 на 31), шаг вернулся. Теперь правила coder'а и tester'а называют единицу: строка на
объявление; у параметризованного теста, где адаптер считает случаи, — на случай, и одна проба метода
служит случаям, которые её прогон показал красными (фильтр по аргументам `[TestCase]` хрупок —
адаптер mewria советует `FullyQualifiedName~Класс.Метод`); где адаптер считает вызов (ts: `it.each(…)`
с таблицей), — одна строка. Ошибка показывает первые пять объявлений по файлу («ещё K» за ними) и
ту же фразу о единице.

**G-101, отчёты инструментов.** В T-16 coder запустил vitest с `--reporter=json`, и в дереве
появился `packages/catalog/.vitest/json/output.json`; coder убрал его сам, иначе файл ушёл бы в
коммит шага. Конфиг vitest Swarga AI Studio `outputFile` не задаёт, а json-репортер vitest без
`outputFile` пишет `output.json` в каталог отчётов пакета (ревью сверило по исходнику vitest 5.0.3).
Теперь адаптер ts называет `--outputFile={SCRATCH_DIR}/{метка}/vitest.json`, при нескольких файловых
репортерах — путь на каждый (`--outputFile.json=… --outputFile.junit=…`: строковый путь vitest
отдаёт всем, и отчёты затирают друг друга), и `--coverage.reportsDirectory=…`; правило «Временные
файлы» coder'а и tester'а — явный путь в `SCRATCH_DIR` для любого отчёта инструмента.

**Ошибка 0.9.4, база слияния.** В `report.py check` база слияния (`base = sync_base(…)`, 0.9.4)
затиралась переменной с тем же именем — каталогом копий проб (`probe_copies_left`, 0.9.1). Счёт
синхронизации получал вместо коммита путь, `git show` не находил файл, и итог сравнивался с суммой
сторон без вычета базы: строка базы, которую сохранили обе стороны, считалась дважды. Ложных новых
тестов это не давало (счёт только мягче), поэтому тесты 0.9.4 и реплей T-16 прошли; терялся повтор
такой строки coder'ом — новый тест или новая не-ASCII строка. Найдено на тесте G-5: файлы другой
стороны попали в «вне слияния». Реплей синхронизации T-16 (8504e2c, `merge --no-ff --no-commit
613c7d6`, разрешение из fc64a1e, настоящий `implement-sync1.md`) на 0.9.6 даёт тот же один
настоящий новый тест («ровно 28 имён» в `index.test.ts`) — теперь с самим объявлением в ошибке.

**Вывод не в UTF-8.** Тестовый файл в latin-1 в `git diff` ронял `report.py` с `UnicodeDecodeError`,
а необработанное исключение Python — код 1, тот же, что «вернуть отчёт агенту». Теперь
`omixflow_lib.git` и `git_raw` читают вывод с заменой байтов, а падение `report.py` — код 3.

## 3. Цена и совместимость

- Новых фаз, проходов и агентов нет. Синхронизация: одна базовая линия перед заданием coder'у;
  в `check` — два `diff --name-only`, без baseline ещё `cat-file -e` на файл вне слияния.
- Слепое пятно без baseline: правку coder'а в файле, который есть в HEAD и которого слияние не
  касается, `check` не сверяет — только предупреждает. С baseline его нет. Новый неотслеживаемый
  файл разработчика без baseline по-прежнему идёт на coder'а.
- Ревью выпуска нашло, что первая версия G-5 выводила из дельты и новые файлы coder'а (на 0.9.5 они
  сверялись) — исправлено до слияния, тест `test_a_file_the_coder_makes_during_the_sync_is_his`.
- `plan.py check` до Implement (`steps_done` пуст) работает как прежде.
- Коды выхода: `report.py check --conflicts none {файл}` и `--conflicts ""` — 3; падение `report.py` —
  3 вместо 1.
  Остальные прежние.
- `report.py check`: текст ошибки MUTATIONS длиннее (объявления и единица счёта); вне синхронизации
  дельта прежняя.
- Агенты читаются при спавне, скилы — при загрузке: идущие задачи получат правила со следующего
  спавна агента; continuation-агенты остаются на своих.

## 4. Что проверить на следующих прогонах

- `plan.py check` посреди Implement: строка о сделанных шагах и ни одного «already exists» по их файлам.
- Синхронизация при грязном дереве (mewria, R-2): без возврата за чужой не-ASCII; предупреждение
  «вне слияния» в вердикте — признак, что базовую линию перед заданием coder'у не сняли.
- MEW-подобные шаги с `[TestCase]`: MUTATIONS с первого круга по случаям.
- Ни одного `.vitest/`, `junit.xml` или `coverage/` в TREE STATE отчётов.

Не вошло (бэклог): `state.py step … done 3a` не принимает шаги с буквой (G-97 для них не
работает); корень проекта в подкаталоге git-репозитория — пути `git diff` от корня репозитория.
